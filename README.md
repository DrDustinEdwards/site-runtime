(`./ai-gateway`), starting a Claude Code routine (`./routine`), the check on AI-written prose with the measure of an author's voice (`./prose`), the one sign-in every site
offers (`./sign-in`, `./sign-in-client`, `./apple-secret`), the Cloudflare Turnstile widget and its server check (`./turnstile`), the same-origin check for

No dependencies (`./sign-in` uses the site's own `better-auth` and

## Security headers

OWASP's defaults for every header that is the same everywhere, a Content-Security-Policy built from a short per-site list
of what the site loads, and the check that proves a site's responses carry them. Every site adopts it.

## The defaults, and what is not in them

`STANDARD_SECURITY_HEADERS` is OSHP's recommended set, in OSHP's words, minus four it recommends and this package does not
put on every response (`OWASP_SKIPPED` carries each reason in code):

| Skipped | Why |
| --- | --- |
| `Cache-Control: no-store, max-age=0` | Sent on every response it makes nothing cacheable, edge caches included. A site sets caching per route. |
| `Clear-Site-Data` | Sent on every response it wipes the reader's cookies, storage and cache at each page load. It belongs on the logout response only: a site's sign-out sends `LOGOUT_HEADERS` (the sign-in's sign-out hook does). |
| `Cross-Origin-Embedder-Policy: require-corp` | It refuses every cross-origin subresource that does not opt in with CORP or CORS, which breaks images, fonts and scripts a normal site loads elsewhere. Every registry site declares `coep` in its entry (`{ value: "credentialless", reportOnly: true }` to start), and `buildSecurityHeaders` writes it with `report-to="csp-endpoint"`, so what it refuses, or would refuse, reaches the sink. |
| `Content-Security-Policy` | A policy names what a site loads, so it is not one string for every site. It is built per site (below). |

A site that must differ on another header says so in `overrides`, each with a reason in the same place:

```js
const SECURITY_HEADERS = buildSecurityHeaders({
  overrides: {
    "Cross-Origin-Resource-Policy": { value: "cross-origin", reason: "og:image previews load this site's images from other origins" },
  },
});
```

`buildSecurityHeaders` refuses an override with no reason, an empty value, one that restates the standard, and the removal of
a header the standard does not send, so the list stays the list of real deviations.

**Cookies.** `hostCookie(name, value, { maxAge, sameSite, httpOnly })` writes a `__Host-` cookie: `Path=/`, `Secure`,
`HttpOnly` unless `httpOnly: false`, and `SameSite=Lax` or `Strict`. It refuses a name that already has a prefix, a name or
value a cookie cannot carry, and `SameSite=None`. The check fails a cookie without a prefix unless the entry declares it
(`deviations: { K1: { reason, value: [names] } }`), and a response that sets one must be `no-store` or `private` (X1).

**Uploads.** `UPLOAD_HEADERS` is the pair every uploaded file carries: `nosniff` and a policy with `sandbox` and
`default-src 'none'`, so an SVG or HTML file opened on its own runs no script. `./image` sends it on every file it serves.

## The site registry

`./sites` holds one entry per live site with only its declared deviations, each with the reason the site's code gives:
header `overrides` in the shape above, and the policy opt-ins the check must accept (`cloudflareWebAnalytics`,
`inlineScripts`, `inlineStyles`, `formTargets`, `framedBySameOrigin`, `baseUriSelf`, and `passkey`, which applies
`PASSKEY_OVERRIDES`). Every registry site is graded on five items whether it opts in or not: Integrity-Policy (S2), a
strict script policy (C3: `'strict-dynamic'` beside a nonce or hash, or no script at all), Trusted Types (C7),
`default-src 'none'` (C9) and COEP (I3). A site meets each, stages it, or declines it in `deviations` with the reason its
code gives, so the registry is the whole list of what each site skips. The opt-ins that meet or stage them are promises
the check holds the site to: `strictDynamic`, `trustedTypes` (`true` or `"report-only"`), `denyUnlisted` (`true` or
`"report-only"`), `integrityPolicy` (`"enforce"` or `"report-only"`, which `buildSecurityHeaders` writes) and `coep`
(which it writes too); a `"report-only"` `trustedTypes` or `denyUnlisted` is met by the Report-Only policy
(`buildStagedPolicy`). `uploads` is a path prefix the live check samples for A3. `deviations` names a checklist item the
site does not meet, with its reason (`{ reason, value? }`); the check and the live check then warn instead of failing.
`oldSite` is the real domain while it still serves the live old site the Worker replaces: a site served from workers.dev
is noindexed there while, and only while, it has one (A6). `assets` says how the static files get their headers (below). `FAMILY_DEVIATIONS` are the ones true of every site (no OpenPGP key to sign
security.txt, HSTS on the http hop, no session for R4), printed as notices, which count as nothing. The
builder and the check read the same entry, so a site cannot build one set and be graded against another. Each entry is
its own export, so a Worker imports its entry by name and bundles that entry, not the registry:

```js
import { mySite } from "@dustinedwards/site-runtime/sites";             // the site's own entry, by its export name
const SECURITY_HEADERS = buildSecurityHeaders({ site: mySite });        // the standard with the site's declared deviations
checkSecurityHeaders(response.headers, { site: "my-site" });            // graded against exactly that, opt-ins included
```

A deviation an audit marked as a gap is left out of the registry on purpose, so the check fails it until the site is
fixed: dustinedwards.info's nine-feature Permissions-Policy and one-year HSTS, germomics' Permissions-Policy allowances and
wildcard script hosts, and `Cross-Origin-Resource-Policy: cross-origin` on every response. `overrides` still works for a
site that has not moved to its entry; `site` and `overrides` together are refused. COEP is in each entry, not the standard.

**CORP per response kind.** `headersFile(set, { charset: true })` writes it for static files, so a site needs no rule of
its own. `corpFor(contentType)` (`./headers`) is `cross-origin` for public media other origins load (an
image, a font, a stylesheet or script, an RSS, Atom or JSON feed) and `same-origin` for everything else, so a site marks
those responses and not every response. A stylesheet must be `cross-origin` for a sandboxed frame (an opaque origin,
such as Carrel's preview) to load it. The check accepts `cross-origin` on those kinds only.

## The policy, from a list of what the site loads

```js
const { name, value } = buildContentSecurityPolicy({
  sources: { img: ["data:"], media: ["https://media.example.com"] },
  scriptHashes: [await scriptHash(inlineLoaderText)],   // an edge-cached page: hashes, never a nonce
  nonce,                                                 // a page that is never shared-cached: generateNonce()
  styleAttributesInline: true,                           // style="" attributes, which a nonce cannot cover
  cloudflareWebAnalytics: true,                          // the beacon, once, here
  reportOnly: false,                                     // true ships the policy as Content-Security-Policy-Report-Only
});
headers.set(name, value);
headers.set("Reporting-Endpoints", reportingEndpoints(CSP_REPORT_GROUP, new URL(CSP_REPORT_PATH, url.origin)));
```

Every site reports to `CSP_REPORT_PATH` (`/csp-report`) under the group `CSP_REPORT_GROUP` (`csp-endpoint`): the
builder's `reportUri` and `reportTo` unless given (a page that reports to another host names the full URL), the group
COEP and Integrity-Policy report to, and what the check expects of a registry site (C14).

`reportingEndpoints(group, url)` writes the header that defines the `reportTo` group. The URL must be absolute and
[potentially trustworthy](https://w3c.github.io/webappsec-secure-contexts/#is-origin-trustworthy): https, or http on a loopback
host (`127.0.0.0/8`, `[::1]`, `localhost`, `*.localhost`), so a local dev server needs no special case. A browser skips any
other endpoint, and the group's reports then go nowhere, so the function refuses it.

The fixed parts are the same for every site: `default-src 'self'`, `object-src 'none'`, `base-uri 'none'`,
`form-action 'self'`, `frame-ancestors 'none'` (`framedBySameOrigin: true` makes it `'self'`, for a site that frames its own
pages, such as Capsomer's specimens; pair it with an `X-Frame-Options: sameorigin` override). Two make it stricter:
`denyUnlisted: true` writes `default-src 'none'`, so a kind the policy does not name (media, frames, workers, the manifest)
is refused rather than allowed from the site, and `noForms: true` writes `form-action 'none'`, for a site with no forms.
`formTargets` adds https origins to `form-action 'self'` for a form whose POST redirects off the site (Stripe Checkout,
Connect OAuth): browsers apply form-action to every redirect hop of a native submission, so `'self'` alone refuses one
made before hydration or with no JS. Each is one bare https origin (no wildcard, path or `http:`), and none goes with
`noForms`; declare the same list in the site's registry entry.
`baseUriSelf: true` writes `base-uri 'self'`, for a page that sets a same-origin `<base>` (Foxing's EPUB reader). Scripts are `'self'`, the
site's hashes or nonce, its listed hosts and, on request, the Cloudflare Web Analytics beacon. In every kind, a source of
`*` (or `https://*` and the like), a wildcard subdomain (`https://*.example.com`) or a bare network scheme (`https:`) is
refused, and so are `data:` and `blob:` where script runs; `broadSource(source, directive)` is that one rule, shared with
the check. `'unsafe-inline'` or `'unsafe-eval'` as a script source, in any case, is refused, and a policy always has both
report sinks: `reportUri` for browsers without the Reporting API and `reportTo` for the rest. `'unsafe-inline'` reaches script-src only through the named opt-in below. `extraDirectives` adds a
kind the builder leaves out (`worker-src`, `manifest-src`, `upgrade-insecure-requests`). One the builder writes is refused,
since a browser silently ignores a second directive of the same name: `default-src`, `script-src`, `style-src`, `font-src`,
`img-src`, `media-src`, `connect-src`, `frame-src`, the fixed ones and the sinks, and with them the `-elem` and `-attr`
variants of `script-src` and `style-src`, which would reopen scripts or styles past the nonce. Frames and media go in
`sources.frame` and `sources.media`; without them, `default-src` covers the site's own.

**Strict dynamic.** `strictDynamic: true` puts `'strict-dynamic'` on script-src, so the scripts the nonce or hashes trust may
load others (a bundler's route chunks) without listing them. A browser then ignores `'self'` and every host source, so the
builder refuses it without a nonce or script hashes (nothing would run) and beside `cloudflareWebAnalytics: true` (the edge
injects the beacon with no nonce, so it would be blocked). `'strict-dynamic'` as a raw script source is refused: the option
is the one way to write it.

**The beacon.** Cloudflare's edge injects `/beacon.min.js/v31...` into a proxied site's pages, so the script source is the
host with a path prefix, not the bare file: `https://static.cloudflareinsights.com/beacon.min.js` and the same followed by `/`
(`CLOUDFLARE_WEB_ANALYTICS.script`). It reports to the site's own `/cdn-cgi/rum`, so `connect-src` always carries `'self'`.
The file is named and not hashed because its `integrity` changes whenever Cloudflare ships a new beacon.

**Nonce or hash.** A response that is never shared-cached may carry a per-request nonce (`generateNonce`).
An edge-cached response must not send its stored nonce again: every reader would share one for the cache lifetime. Either
its inline scripts are trusted by hash (`scriptHash`), or it keeps the nonce and `renewNonce(response)` gives every response
a fresh one, in the policy header and on every `<script>`, `<style>` and `<link>` that carried the rendered one (an element
injected without it gains none). Call it on every response the cache answers. It uses HTMLRewriter, and throws outside
Workers rather than resend the stored nonce; Foxing's edge cache works this way.

**Trusted Types and staged rollout.** `trustedTypes: true` writes `require-trusted-types-for 'script'`; a list of names adds
`trusted-types <names>`. Ship it Report-Only first: `buildStagedPolicy(site, { trustedTypes: ["default"] })` returns the
site's own policy with the staged part added as `Content-Security-Policy-Report-Only`, sent beside the enforced one until
the reports are quiet, when the staged part moves into the enforced policy.

**Integrity-Policy.** `integrityPolicy({ endpoint, reportOnly })` (also on the root export) returns `Integrity-Policy` (or `-Report-Only`) with
`blocked-destinations=(script)` and `endpoints=(<group>)` (`csp-endpoint` unless given), so a script without an `integrity`
attribute, or fetched no-cors, is refused. Every bundle, dynamically imported chunks included, needs build-time integrity
first, so start Report-Only. A site declares `integrityPolicy` in its entry and `buildSecurityHeaders` writes the header.
React Router writes the integrity with `subResourceIntegrity: true` in `react-router.config.ts` (stable in 8.5): an
import map with every chunk's hash and `integrity` on each modulepreload. The import map is an inline `<script>` that
carries the page's nonce, so `renewNonce` renews it with the rest; a page trusted by hashes instead needs the import map's
hash. A static build writing its own tags gives each `integrity` from `integrityHash(bytes)` (sha384) and `crossorigin`,
which a classic script needs, since Integrity-Policy refuses a no-cors script whatever its integrity. A Vite build (Capsomer's site, the Capsid
Portal) writes neither: `subresourceIntegrity()` (`./sri`) is the plugin that gives every `<script src>` and
modulepreload the build wrote for its own files their sha384 and `crossorigin` once the build is written, and
`writeIntegrity(dir, { base })` the same pass over any built folder (the Capsid explorer's). A module script's static
imports, transitively, get a modulepreload with their integrity when the page has none for them, since an import map
would be an inline script. A module loaded with `import()` gets no integrity from either (only an import map gives it
one), so it shows in the reports before enforcing. The live check warns
on any off-site script or stylesheet the home page loads without `integrity` (S1).

**Inline scripts, the last resort.** `inlineScripts: "unsafe-inline"` puts `'unsafe-inline'` on script-src. Use it only when
neither a nonce (with `renewNonce` on a cached page) nor hashes can work. A nonce is preferred, then hashes. The builder refuses
it beside a nonce or script hashes, because a browser then ignores `'unsafe-inline'` and the page's inline scripts stop
running. The check fails such a policy unless the site's registry entry declares the same opt-in, which accepts it on script-src
alone. Inline `<style>` elements, when a site has them
and no nonce, are a style source like any other: `sources: { style: ["'unsafe-inline'"] }`. A page with a nonce whose
styles must stay inline (a browser ignores `'unsafe-inline'` beside a nonce) passes `nonceStyles: false`, which keeps the
nonce on script-src only.

A policy for one kind of document rather than a page (a sandboxed image route, an SVG opened on its own, a preview, an OAuth
consent page) is written with `buildPolicy`; the page builder does not take options for those.

## The report sink

Every policy needs both sinks, and every site receives its reports with the same function (`./csp-report`), not its own,
at `/csp-report`. It keeps the three kinds a site's headers ask for: CSP violations, Integrity-Policy's
`integrity-violation` and COEP's `coep`; other Reporting API types (deprecation, intervention) are dropped.

```js
import { receiveCspReport } from "@dustinedwards/site-runtime/csp-report";
if (url.pathname === "/csp-report") return receiveCspReport(request, { headers: SECURITY_HEADERS, allow: (r) => myLimiter(r) });
```

A POST always gets 204 (an error status makes browsers send the report again). The body is read to 16 KB and no further;
at most 10 reports are logged, one JSON line each (`event` is the report's type; `directive` the CSP directive,
`blocked-destinations` or the COEP check), with every URL cut to its origin and path, and no address, user agent or cookie. `allow` is the site's rate limiter, asked before the body is read; `allowOrigin` names the one origin
that may report from another host (the CORS preflight). Nothing is stored.

A violation whose blocked URL or source file is an extension's or the browser's own (`chrome-extension:`, `moz-extension:`,
`safari-extension:`, `safari-web-extension:`, `ms-browser-extension:`, `resource:`, `file:`, `jar:`, `about:`) is dropped:
the site can do nothing about it ([Dropbox](https://dropbox.tech/security/on-csp-reporting-and-filtering)). The first time an
isolate sees a (directive, blocked origin) pair it logs `csp_new_blocked` as a warning, the event a log alert watches for a
newly blocked host.

Pass `allow`. A receiver without it still works, since Capsomer calls it that way today and refusing would end its reports
in silence, but it logs `csp_report_unlimited` once per isolate as a warning, so the gap shows in the site's logs.

## A request body, read to a ceiling

`./body` reads a body to a byte ceiling, counting the chunks as they arrive. Content-Length can be missing or wrong,
and `request.text()` holds the whole body before any check runs, so neither is a cap.

```js
import { readCapped } from "@dustinedwards/site-runtime/body";
const text = await readCapped(request, 64 * 1024);
if (text === null) return new Response("too large", { status: 413 });
```

`null` means over the ceiling (never a truncated body); "" means no body; a stream that fails mid-read throws.
`readCappedBytes` returns the bytes instead. The report sink above reads with it.

`requireJson(request)` is `null` for an `application/json` (or `+json`) body and otherwise a 415, `no-store`, so a JSON
route never parses a form a cross-site page could post without a preflight.

## HTML escaping

`./html` is the one `escapeHtml`.

```js
import { escapeHtml } from "@dustinedwards/site-runtime/html";
const html = `<a title="${escapeHtml(title)}">${escapeHtml(label)}</a>`;
```

It replaces `& < > " '` with `&amp; &lt; &gt; &quot; &#39;` and nothing else, so its output is safe as element content and
inside a single- or double-quoted attribute. A non-string is passed through `String()` first, as a template literal would.
It is not an encoder for unquoted attributes, `javascript:` URLs, or the inside of `<script>` and `<style>`.

## AI-written prose and the author's voice

`./prose` is for every app that has a model write text a person will read (Carrel's drafts, Foxhound's emails). It flags;
the caller decides what a flag means.

```js
import { checkProse, profileOf, nearestPassages, distanceFrom, thresholdFor, copiedRuns, WRITING_RULES } from "@dustinedwards/site-runtime/prose";

const issues = checkProse(body, { phrases: authorList, allow, dashes: "flag", firstLine });
const profile = profileOf(publishedPosts); // null under ~900 words
const examples = profile ? nearestPassages(profile, publishedPosts, 5) : [];
const unlike = profile && (distanceFrom(profile, draft)?.distance ?? 0) > thresholdFor(profile);
const copied = copiedRuns(draft, examples); // runs of 8+ words lifted from the excerpts
```

- `checkProse` flags `TELLS` (phrases current models still write, each with what to do instead) and `OUT_OF_PLACE`
  (their blurb and email words), the caller's own `phrases`, the "not X, it's Y" construction across two sentences, a
  paragraph closing on a list of three and each dash on its line (an unspaced en dash is a range and passes). Each issue
  has `check`, `message`, `excerpt`, `line`, `severity` and `sign`, the section of Wikipedia's "Signs of AI writing" it
  falls under (`SIGNS`). `allow` takes a word back out of every list.
- `PATTERNS` are errors whoever wrote the rest, so they are high: a refusal or knowledge-cutoff note, an unfilled blank
  (`[Your Name]`, `2025-XX-XX`) and chatbot markup (`oaicite`, `utm_source=chatgpt.com`). Code is skipped. `slopScan`
  reports them as `filler`.
- The lists hold only what current Claude models were seen to write, with no style rules, on 2026-10-25: blurbs, bios,
  a companion's replies, UI copy, newsletters, failed-payment and win-back emails, a dispute statement and dashboard
  summaries (Capsid `foxing/ai-writing-tells.md`). The older lists ("delve", "tapestry", "I hope this email finds you
  well") and the avoid-ai-writing engine are gone: those models no longer write them, and a list that flags nothing a
  model writes only flags people. Re-run the sample when the models change.
- `profileOf`, `distanceFrom`, `describeFeature` and `VOICE_THRESHOLD` measure a text against the author's own passages in
  the manner of Burrows' Delta: sentence length, punctuation, contractions and 48 function words. `thresholdFor` widens
  `VOICE_THRESHOLD` to the author's own spread, so an author whose posts vary a lot is not flagged for being themselves.
- `copiedRuns` finds a draft's word runs copied from the examples: the model should borrow the voice, not the facts.
- `nearestPassages` picks one excerpt per post, the passages that read most like the author's usual style. Those, `WRITING_RULES` and the
  author's own guide are what a model reads before it writes: real examples copy a voice better than a description of it
  (Wang et al., Findings of EMNLP 2025).

`slopScan(draft, excerpts, { firstLine, sources })` is the scan after a draft. It measures the
author's sentence lengths from their own excerpts (`sentenceSpread`: 10th percentile, median, 90th, longest) and returns
at most twelve findings, each `{ kind, excerpt, line, say }`, plus one `instruction` a session can apply in place:

- `length`: a sentence eight or more words past the author's long ones and past their longest; four or more sentences in
  a row within two words of each other, when the author's own run at least ten words apart (a run of fragments at or
  under their short length is a device and passes);
- `filler`: a phrase in `TELLS`, with what to do instead;
- `word`: an `OUT_OF_PLACE` word, flagged only when the excerpts never use it;
- `shape`: a joiner dash, "not X, it's Y" and "a gift, not a waste", a paragraph ending on three padded words, a paragraph
  ending on a stinger of two to five words, a sentence opened with "So", "And" or "But", a bold lead-in ("**You can't skim
  out loud.**"), and a question put to the reader, each only when the excerpts do not write that way themselves (a dash
  between numbers is a range); and, in every draft whatever the excerpts do, a first sentence that is a definition, a last
  sentence that sums up ("This is one reason that") or asks the reader something ("Want to look at it together?"), and the
  passive voice;
- `detail`: a paragraph of 25 words or more with under half the specifics (numbers, names, places) of the excerpts'
  plainer paragraphs (their 10th percentile); DNA, RNA, PCR and the like are kinds of thing, not specifics;
- `source`: with `sources` (the text of the papers and pages the draft drew on), each sentence holding a name or number
  found in neither the sources nor the excerpts, since a claim nobody can check is the one a reader cannot trust; with
  `sources` empty, one finding asking for them. Without `sources` the check is off.

Pass every passage of the author's own writing as `excerpts` when there is more than a model reads: the measures are
steadier on more of it, and a long sentence of theirs that the chosen excerpts leave out is still theirs.

`voiceExcerpts(passages, count)` picks the excerpts a model writes from: one per passage, one holding a long sentence of
the author's and one a short one, the rest the newest. The excerpts nearest the average show a model one length.

Nothing here scores text against an AI detector or aims to pass one.

## The /health response

`./health` is the uptime probe's answer, in the IETF health check draft's shape (draft-inadarei-api-health-check-06,
`application/health+json`): `healthResponse({ ping, backup, sha, checks, backupTtlMs, checkTimeoutMs, now })`, every
field optional, with `{ status, ok, alerts, db, backup, sha, time, checks: [{ name, status, detail, alert }] }`,
`no-store` and `noindex`.

```js
import { healthResponse, r2Check } from "@dustinedwards/site-runtime/health";
import { cronCheck } from "@dustinedwards/site-runtime/cron";
return healthResponse({
  ping: () => env.DB.prepare("SELECT 1").first(),
  backup: () => backupHealth(env.BACKUPS),
  sha: env.DEPLOY_SHA,
  checks: [r2Check("media", env.MEDIA), cronCheck(env.DB), { name: "drift", level: "warn", run: contentDrift }],
});
```

- A check is `{ name, level, alert, run }`, `level` "fail" by default or "warn". It fails when `run` throws, rejects, resolves
  `false` or resolves `{ ok: false, detail }`, or does not answer within `checkTimeoutMs` (3000 by default), so /health
  never hangs on a binding. A thrown error's text is the detail, scrubbed by `./log` and cut to 200 characters; a failed
  "fail" check is logged as `health_check_failed`.
- `ping` is check `db` (level fail) and the body's `db: "up" | "down"`; a site with no database leaves it out. The
  backup is check `backup` (level warn), failed when its status carries a `warning`.
- `status` is fail when a fail check failed, else warn when a warn check failed, else pass. 503 only for fail: a stale
  backup, a stopped cron or content drift is warn and 200, because the site is up. `ok` is `status !== "fail"`, so a
  keyword monitor on `"ok":true` pages only when the site is down; a warning is in `status` and the checks.
- An alert (`alert: true` on the check) is a failure someone must hear of now while the site is up. It keeps its
  level, warn, so the response stays 200 and `ok` true and devkit's worker-deploy, which rolls back when /health is not
  ok, never rolls a deploy back for it; its result carries `alert: true`, `alerts` names it, and it is logged as
  `health_alert`. A watcher (Capsid's) keys on `alerts` to raise a finding and mail a person.
- `r2Check(name, bucket)` and `kvCheck(name, kv)` are the binding checks: a `head` or `get` of a fixed key, where no
  object is fine and a throw fails.
- `imagesCheck(name, env.IMAGES)` asks the Images binding for `info` on a 1 x 1 GIF (it reads the header and
  transforms nothing). `durableObjectCheck(name, env.ROOM)` proves the namespace is bound and mints an id with
  `idFromName`; it sends no request, which would wake an object and bill it. `queueCheck(name, env.QUEUE)` and
  `aiCheck(name, env.AI)` prove the binding is there and send or run nothing (a probe message would reach the consumer,
  and every AI call is billed). All four are level warn; spread one with `level: "fail"` to make it take the site down.
- `authSpikeCheck(env.DB, { windowMinutes: 60, failures: 50, mails: 50 })` is the sign-in spike alert (F3), level
  warn and an alert: it fails when failed sign-ins (`authn_login_fail`) or sign-in mails (`authn_token_created`) in the
  window pass their ceiling, read from `./sign-in`'s `auth_events` table (`eventsDb`), with the counts as its detail.
  /health names it in `alerts`, and the watcher mails on it.
- `sha` is the deployed commit, when the site knows it. The backup read is held per isolate for `backupTtlMs` (five
  minutes by default; 0 reads every time), because listing the R2 bucket is a billed Class A operation and the route is
  public.

## Responsive images

`./image` is a site's images end to end: the attributes a page writes and the route that serves each size from the one
original in R2 through the Images binding. One `defineImages` call names each way the site shows images, so the page
never asks for a size the route would refuse:

```js
import { defineImages, pictureHtml } from "@dustinedwards/site-runtime/image";

export const images = defineImages({
  uses: {
    content: { layout: "constrained", width: 704 },   // the prose column
    cover: { layout: "full-width", ratio: "16x9" },    // cut around the file's focal point
    tile: { layout: "fixed", width: 160, ratio: "1x1" },
  },
});

// The page: srcset, sizes, width, height, and AVIF then WebP sources for a <picture>.
const attrs = images.attributes({ src: "/media/photo.jpg", width: 2400, height: 1600, focus: "0.4x0.3" }, "content");
const html = pictureHtml(attrs, { alt: "The lab bench", priority: true }, escapeHtml);

// The route, /media/*: the original, or one size for ?w=.
return images.respond(request, { object: await env.MEDIA.get(key), images: env.IMAGES, cache: caches.default, reread: () => env.MEDIA.get(key) });
```

The widths and the three layouts are Astro's (MIT, credited in `image.mjs`): `constrained` offers the use's width, twice
it and every screen width between (`SCREEN_WIDTHS`), `fixed` offers 1x and 2x, `full-width` every screen width, and none is
ever wider than the original. `sizes` follows the layout.

`breakpoints` replaces `SCREEN_WIDTHS` for every use. A site moving here with widths already in pages, feeds or caches
passes them, so those URLs stay inside the closed set: dustinedwards.info's `?w=1024` links keep working with
`breakpoints: [640, 1024, 1408]` (its 704 content use then serves 640, 704, 1024 and 1408). A width dropped from the set
is a `400` for every page that still links it.

Every set is closed. The binding bills each unique source and parameter set once a month (5,000 free, then $0.50 per
1,000), so a width, format, crop or focal point outside the site's own set is a `400`, never a transform. Format and
quality are not counted, so the AVIF and WebP of one size bill once. The format is in the URL (`f=avif`), never read from
`Accept`, because the edge cache is keyed by URL alone. A crop's URL carries the file's focal point (`fp=`, from the R2
object's `focus` custom metadata), and the route refuses one that is not the file's own, so a moved focal point is a new
URL rather than a stale crop. The edge cache key also carries the original's etag, so a file replaced under the same key (site-api's `PUT
/media/:id/file`) is a new key for every size and nothing cached from the old bytes is served again; browsers that
already hold a size or the original under `immutable` keep it until it expires. Quality 85 is always passed; without it the binding writes lossless WebP, larger than the
original. An SVG is only ever served as an attachment. Without the binding (a checkout with no `images` in its
`wrangler.jsonc`) the route serves the original and says so in `x-image`; a failed transform serves the original for five
minutes and logs `image-transform-failed`.

A page that renders JSX takes the same picture as props: `pictureProps(attrs, { alt, priority, className })` returns
`{ sources: [{ type, srcSet, sizes, media }], img: { src, srcSet, sizes, width, height, alt, className, loading,
fetchPriority, decoding } }`, plain objects with no React import, and `pictureHtml` is those props written out, so the
two never differ. An unset prop is `undefined`, which JSX leaves out; with no `sources` the page writes the `<img>`
alone (germomics' `Picture` falling back to the original). A site adds its own props beside them, as julieedwards.info's
`object-position` from the focal point:

```jsx
const { sources, img } = pictureProps(images.attributes(photo, "content"), { alt: photo.alt });
<picture>
  {sources.map((s) => <source key={s.type + (s.media ?? "")} {...s} />)}
  <img {...img} style={{ objectPosition: objectPosition(photo.focus) }} />
</picture>
```

A GIF stays animated. The binding keeps every frame unless `output()` is given `anim: false`, and writes them as
animated WebP; Cloudflare's formats list (Images, Limits) gives animation for WebP and GIF output and not for AVIF, so a
GIF is offered no animated AVIF. For WCAG 2.2.2 and Lighthouse's "use video formats for animated content", a GIF's
`sources` lead with its first frame under `media="(prefers-reduced-motion: reduce)"` (AVIF then WebP, `still=1` in the
URL, which the route writes with `anim: false`), then the animated WebP. `still=1` is in the closed set for a GIF only:
it is a second billed transform of each size, so the route refuses it, and any other value, for every other file. An
animation over 50 megapixels in all its frames is served by Cloudflare untransformed. A long animation is still better
as a `<video>`.

`editImage(images, input, { rotate, flip, maxEdge, format, quality })` is the one edit a site writes back: a turn (`rotate`
90, 180 or 270, clockwise), a mirror (`flip` `"h"`, `"v"` or `"hv"`, which Cloudflare applies before the turn), or a
shrink (`maxEdge`, the longest edge, never enlarged), encoded as `format` at quality 85 unless said; a `format` alone
re-encodes the picture as it is (site-api's upload turning HEIC into JPEG). `input` is a stream or bytes; the answer is
the binding's `Response`. It is for writes a person asked for (an editor's turn, an upload shrunk or converted before it
is stored, a small copy shown to a model), each a billed transform; serving sizes stays with `respond` and its closed
sets. A bad option throws before the binding is called.

```js
const turned = await editImage(env.IMAGES, object.body, { rotate: 90, format: "image/jpeg", quality: 92 });
const shrunk = await editImage(env.IMAGES, bytes, { maxEdge: 4096, format: "image/webp" });
const jpeg = await editImage(env.IMAGES, heicBytes, { format: "image/jpeg" });
```

## Link prefetch

`./prefetch` starts loading the next page while the reader's pointer rests on its link, as Astro's `prefetch` does,
with no script: Chrome and Edge read speculation rules from a file the `Speculation-Rules` header names, and other
browsers ignore it. The header needs no CSP allowance (an inline rule set would need one on every page).

```js
import { SPECULATION_RULES_HEADER, SPECULATION_RULES_PATH, speculationRulesResponse } from "@dustinedwards/site-runtime/prefetch";

if (url.pathname === SPECULATION_RULES_PATH) return speculationRulesResponse({ exclude: ["/drafts"] }, request);
// On every HTML response, beside the security headers:
headers.set(SPECULATION_RULES_HEADER.name, SPECULATION_RULES_HEADER.value);
```

The rules cover same-origin links except `NEVER_PREFETCH` (`/admin`, `/api`, `/auth`, `/logout`, `/sign-out`,
`/cdn-cgi`), the site's own `exclude` prefixes, links to files (`FILE_EXTENSIONS`: feeds, data, documents, archives
and media such as `.md`, `.xml`, `.json`, `.txt`, `.rss`, `.pdf`, `.zip` and `.png`, lower case only), links with a query
string (`excludeQueries: false` lets them through), downloads, links with a `target`, `rel=nofollow` and anything inside
`data-no-prefetch`. A prefetch is a real GET, so a link that acts on a GET must be excluded. `eagerness` is `moderate` by
default; `prerender: true` also prerenders on press, off by default because a prerendered page runs its scripts and
analytics before the reader arrives. Checked in Playwright's Chromium under a strict CSP (2026-10-29): a page link is
prefetched; `.md`, `.xml` and `?q=` links are not. The query rule is a URLPattern object naming the pathname and the
search; the glob spellings `/*?*` and `/*\?*` match every link, so excluding them stops all prefetch.

## Preloads and Early Hints

`./preload` takes a site's preloads once and gives both the React Router `links` entries and the `Link` response header
built from the same list. The header is what Cloudflare Early Hints reads: with the zone's Early Hints on (Speed >
Settings > Content Optimization), a 200, 301 or 302 response for a path with no extension (or .html, .htm, .php) that
carries `Link` with rel=preload or rel=preconnect is answered first with a 103 naming them, so the font or image starts
while the Worker still renders. The hints are cached per URI, ignoring the query, and may not be sent for a response
already in cache ([Cloudflare](https://developers.cloudflare.com/cache/advanced-configuration/early-hints/)).

```js
// app/preloads.ts, imported by root.tsx and workers/app.ts
import { preloads } from "@dustinedwards/site-runtime/preload";
import fontUrl from "./fonts/ui.woff2?url";

export const PRELOADS = preloads([{ href: fontUrl, as: "font", type: "font/woff2" }]);

// root.tsx
export const links: Route.LinksFunction = () => [/* the rest */, ...PRELOADS.links];
// workers/app.ts, in the Renderer: appended to HTML only, after any Link a route already sends.
return withPreloadHeader(page, PRELOADS.header, preloads(rootStylesheets(await serverBuild())).header);
```

`rootStylesheets(build)` is the root route's CSS in a React Router server build as preload entries, the stylesheet every
page blocks on. `withPreloadHeader(response, ...headers)` appends each non-empty value to an HTML response's `Link`.

A font is always fetched in anonymous CORS mode, so a font preload without `crossorigin` is a second request for the
same file. Every `as: "font"` entry gets `crossorigin=anonymous` (in the tag and the header) unless it names
`use-credentials`. `{ rel: "preconnect", href: "https://fonts.gstatic.com", crossOrigin: "anonymous" }` adds a
preconnect. An href must be a path or an https URL, ASCII only (percent-encode the rest), with no `<`, `>` or `"`.

## Edge page cache

`./edge-cache` stores a site's public pages at the edge through the Workers cache and drops them by tag when the site
writes: the scheme dustinedwards.info runs. A stored page is handed to every reader, so only a page that is the same
for all of them may be stored: its CSP trusts inline scripts by hash, not a per-request nonce, it sets no cookie and
it shows nothing signed in. Everything else stays `private, no-store`.

```jsonc
// wrangler.jsonc: the gateway runs on every request; the Renderer's responses are stored. No `cross_version_cache`,
// so the Worker version stays in the key and every deploy starts cold.
"cache": { "enabled": true },
"exports": {
  "default": { "type": "worker", "cache": { "enabled": false } },
  "Renderer": { "type": "worker", "cache": { "enabled": true } }
}
```

```js
import { WorkerEntrypoint } from "cloudflare:workers";
import { cacheKey, forReader, forRenderer, publicPageHeaders, purgeTags, settleCacheHeaders } from "@dustinedwards/site-runtime/edge-cache";

// A public route: stored a day, served stale a week while it re-renders, tagged "pages".
export const headers = () => publicPageHeaders();

export class Renderer extends WorkerEntrypoint {
  async fetch(request) {
    const response = await requestHandler(request, context); // then the security headers and the Link header
    return settleCacheHeaders(response, request); // last: anything but a shared 200 leaves private, no-store
  }

  // A purge reaches only the cache of the entrypoint that calls it, so the Renderer purges its own; RPC methods
  // bypass the cache. Never throws; `false` is logged.
  async purgePages(why) {
    await purgeTags(this.ctx.cache, ["pages"], why);
  }
}

export default {
  async fetch(request, env, ctx) {
    // Signed-in paths, APIs and writes answer here, before the Renderer.
    const page = await ctx.exports.Renderer.fetch(forRenderer(request), { cf: { cacheKey: cacheKey(request.url) } });
    return forReader(page, request); // a request with a cookie is told no-store for the browser
  },
};

// In the gateway, after a write that changes a public page. A purge from the gateway itself would clear nothing.
ctx.waitUntil(ctx.exports.Renderer.purgePages("save page /about"));
```

Fresh and stale lifetimes go in `Cloudflare-CDN-Cache-Control`, never `s-maxage`, which implies proxy-revalidate and
stops Cloudflare serving stale. The browser's `max-age` stays 0, because a purge cannot reach a browser. When a
re-render fails, the Workers cache serves the stored page (`Cf-Cache-Status: STALE`) with no `stale-if-error` needed,
as long as nothing sends `must-revalidate`, `proxy-revalidate` or `s-maxage`
([Workers cache](https://developers.cloudflare.com/workers/cache/configuration/)).
`test/edge-cache.test.mjs` holds this for a database outage: with the page stored and D1 down, the re-render's 500
is not stored, and a model of that rule serves the stored page `STALE` until the stale window ends. The error page
readers see after that is Capsomer's `ErrorPage`, not this package's.

What else the scheme does, and the helpers that do it:

- **The key.** `cacheKey(url, { dimensions })` drops `TRACKING_PARAMS` (`utm_*`, `gclid`, `fbclid`, `msclkid` and the
  other click ids and campaign tags) and sorts the rest, so a campaign link gets the stored page. `dimensions` is what
  else a page varies by, such as a theme read from a cookie: `cacheKey(url, { dimensions: { theme } })`.
- **Whole pages only.** `forRenderer(request)` sends a HEAD to the Renderer as a GET, and `forReader` answers it with
  the headers alone. A HEAD that reached a render would give an empty body, and a stored one would serve that blank
  page to every reader (germomics' own cache did, refreshing a stale page with a HEAD). `settleCacheHeaders` refuses to
  store a HEAD's answer as well.
- **Nothing personal.** `settleCacheHeaders(response, request, { publicCookies })` also refuses to store a response with
  `Set-Cookie`, and one rendered for a request with a cookie other than `publicCookies`. `privateRender(response)` is the same for a page
  the gateway renders itself for one reader.
- **Returning readers.** `settleCacheHeaders` stamps a stored page with `Last-Modified`, the time it was rendered. It
  stays the same until a purge or a deploy renders the page again, so `forReader` answers a reader who already holds
  it (`If-Modified-Since`, or `If-None-Match` for a page with its own `ETag`) with a 304 and no body.
- **Cookies that change nothing private.** `forReader(page, request, { publicCookies: ["theme"] })` keeps the shared
  header for a request carrying only those, so the browser may keep the page in its back/forward cache.
- **Pages that change on a schedule.** `publicPageHeaders({ until: nextPublishAt })` keeps a page that lists posts fresh
  no later than the next scheduled one (a minute at least): it goes live with no write to purge on.
- **Purging.** `class Renderer extends withPurgePages(WorkerEntrypoint)` gives the Renderer its `purgePages(why, tags?)`
  RPC method. In the gateway, `purgeAfterWrite(request, response, ctx, why)` asks for it after an accepted write.
  From a cron or a queue, which have no Renderer of their own, `purgeViaRenderer(why)` asks over `exports` from
  "cloudflare:workers". `schedulePurgeHook()` is a site-api publish hook that does that after a schedule changes a page.

```js
class Renderer extends withPurgePages(WorkerEntrypoint) {
  async fetch(request) {
    return settleCacheHeaders(await timedRender(() => render(request)), request);
  }
}
// gateway
const redirect = canonicalRedirect(request, { host: "example.com" });
if (redirect) return redirect;
if (isWrite) {
  const response = await carrel.handle(request, ctx);
  purgeAfterWrite(request, response, ctx, `carrel ${request.method} ${url.pathname}`);
  return response;
}
const page = await ctx.exports.Renderer.fetch(forRenderer(request), { cf: { cacheKey: cacheKey(url, { dimensions: { theme } }) } });
return forReader(page, request, { publicCookies: ["theme"] });
// site-api
createSiteApi({ adapter, key, hooks: [indexNow, schedulePurgeHook()] });
```

## Server-Timing

`./server-timing` puts how long the Worker spent on a response in `Server-Timing`, which DevTools shows and field
monitoring reads. `timedRender(async (marks) => render())` adds a `render` mark; `timed(marks, "d1", fn)` adds one for
a wait inside it. In a Worker the clock moves only across I/O, so the marks measure the waits (D1, R2, fetch), which is
what makes a render slow. A stored page keeps the marks of the render that stored it.

## The images audit

`site-runtime-images --origin <origin> [--from <host>]` checks a live site's images and media as served, with plain fetch and
no browser: the home page and up to 24 sitemap pages, at most 8 originals (2 MB of each) and 6 size URLs a page. Each
finding is a GitHub annotation, `::error title=<item>::<proof URL> <detail>` or `::warning ...`, the contract devkit-live
runs every area's check by; it exits 0 with no errors, 1 with errors, and 2 when it could not run (a bad origin, or a
home page that does not answer 200). `--from` fetches from where the site is served now and judges every URL as the
origin, for a site not yet on its domain.

| Item | Finds |
|---|---|
| A2 | a raster `<img>` wider than 300 px (its width attribute, else the file) with no `srcset` and `sizes` (a `<picture>` source's counts) |
| A3 | a `/media` size URL that does not answer `image/avif` for `f=avif` (not a GIF's: it has none) |
| A4 | an `<img>` without `width` and `height` |
| A5 | more than two `fetchpriority="high"` images on a page, or a lazy one |
| A7 | an original with no srcset more than 1.5 times its width attribute (the size read from the PNG, JPEG, WebP, GIF or AVIF header) |
| A12 | a srcset size URL without `immutable` in Cache-Control |
| B1, B2 | an `<img>` with no alt; an alt that is the file name, "image", "photo" or a URL |
| C1 | og:image missing, not absolute https, not 200 or not an image |
| C2 | og:image not 1200 by 630 (a warning when at least 1200 wide); og:image:width, height, type or alt missing or not the file's |
| C3 | twitter:card not `summary_large_image`; no twitter:image:alt |
| C8 | a warning: a sitemap page with content images (raster, not decorative, in `<main>`) and no `image:image` entry |
| D2 | a JPEG, WebP or PNG original on the site (its host or a subdomain) whose EXIF holds a GPS IFD |
| E1 | a youtube.com (not youtube-nocookie.com) or Vimeo player in the page with no facade; an iframe with no title |
| E2 | a `<video>` without a poster, controls or a captions track, or with `preload="auto"` |
| E3 | a warning: an `<audio>` with a preload other than none or metadata |

It reads the HTML the server sends, so an image a script adds later is not seen. `auditImages` and `readImage` are
exported from the bin for its test.

## Share cards

`./share-card` draws a site's own card HTML to the PNG a link preview shows. workers-og (Satori and resvg) stays the
site's dependency and is passed in: `renderShareCard(ImageResponse, html, { fonts, width, height, headers })` removes the
whitespace between tags (Satori makes it a flex child), draws the card inside a box of its size (so a root at
`width:100%` fills the card rather than shrinking to its text), reads the whole PNG so a failed render is `null` (logged as
`share_card_failed`) rather than an empty image, and answers `image/png` cached a week at the edge, with `headers` added
(Foxhound's `Cross-Origin-Resource-Policy: cross-origin`). `cardText(value)` leaves `&` as is and turns `<` and `>` into
‹ and ›: workers-og shows entities literally, so `escapeHtml` would put "&amp;" or "&lt;" on the card. `googleFont(family, weight, { cache, cacheOrigin })`
fetches one static weight as WOFF (Satori reads TTF, OTF and WOFF, not WOFF2 or a variable font) and keeps it a year in
`cache`. The design, colors and fonts are each site's own. 1200 by 630 is `SHARE_CARD_WIDTH` by `SHARE_CARD_HEIGHT`.

`shareCardResponse(ImageResponse, { html, fonts, cacheKey, cache, ctx, width, height, headers })` is the whole card route:

```js
import { googleFont, shareCardResponse } from "@dustinedwards/site-runtime/share-card";
import { ImageResponse } from "workers-og";

return shareCardResponse(ImageResponse, {
  cacheKey: `https://og.example.com/book/${book.slug}?v=${book.updatedAt}`, // whatever changes the card
  html: () => cardHtml(book),                                              // called on a miss only
  fonts: async () => [{ name: "DM Sans", data: await googleFont("DM Sans", 500, { cache: caches.default }), weight: 500, style: "normal" }],
  ctx,                                                                     // the cache write goes in ctx.waitUntil
});
```

It answers from `cache` (the Workers zone cache unless given) when `cacheKey` is there, else renders with
`Cross-Origin-Resource-Policy: cross-origin` (`SHARE_CARD_HEADERS`: other sites' previews load the card, and the family's
default is same-origin), keeps the PNG under `cacheKey`, and answers a failed render with a 503 (`Retry-After: 300`,
`no-store`), never an empty image. `html` and `fonts` may be values or functions, so a cache hit builds no HTML and
fetches no font. A route that wants another fallback (Foxing redirects to the book's cover) keeps `renderShareCard`.

## security.txt

`./security-txt` writes `/.well-known/security.txt` (RFC 9116), so every site tells a finder where to report a
vulnerability.

```js
import { securityTxtResponse } from "@dustinedwards/site-runtime/security-txt";
return securityTxtResponse({ origin: "https://example.com", contact: "security@example.com", expires: "2027-09-28T00:00:00Z" });
```

`securityTxt(fields)` is the text: Contact (an address becomes a `mailto:` URI), Expires, Policy when given,
Preferred-Languages (`en` unless given) and Canonical. `securityTxtResponse(fields, headers)` serves it as text/plain,
cached for an hour, always as `text/plain; charset=utf-8` (it refuses a Content-Type in `headers`); `headers` adds to or
replaces the rest. Expires is required: prefer a fixed date with a test that fails
a month before it lapses, the prompt to confirm the address still works.

## Byte encodings

`./encoding` is the one set of byte encodings, Web APIs only (no Buffer, no `jose`): `toHex`/`fromHex`,
`toBase64`/`fromBase64` (whitespace ignored, as GitHub wraps it), `base64url`/`fromBase64url` (no padding) and
`sha256Hex`. Every encoder takes bytes or a string, which is encoded as UTF-8.

## Signed links

`./signed-token` is the one stateless token behind links a site emails (unsubscribe, card update, an open pixel):
`base64url(JSON payload).base64url(HMAC-SHA-256)`. It proves integrity, not secrecy, so a payload carries ids, never
anything private, and each caller checks its own payload's fields.

```js
import { readSignedToken, signToken } from "@dustinedwards/site-runtime/signed-token";
const keys = [env.EMAIL_TOKEN_KEY, env.EMAIL_TOKEN_KEY_PREVIOUS]; // hex, newest first
const token = await signToken(keys, { a: accountId, k: "unsub" });
const payload = await readSignedToken(keys, token); // null on any tamper or format failure
```

The first present key signs and every key verifies, so a key rotates without breaking links already in inboxes: put the
new key first, keep the old one after it until the longest-lived link has aged out, then drop it. Empty entries are
skipped. Give links their own key, never one that also encrypts data at rest. No key at all throws: that is a
configuration error, not a bad link.

## Where a site's Anthropic calls go

`./ai-gateway` is the one decision between Cloudflare AI Gateway and Anthropic directly, so every site logs the same way.

```js
import { anthropicRoute } from "@dustinedwards/site-runtime/ai-gateway";
const { baseURL, headers } = anthropicRoute(env, "example");
const client = new Anthropic({ apiKey: env.ANTHROPIC_API_KEY, baseURL, defaultHeaders: headers });
// or, without the SDK: fetch(`${baseURL}/v1/messages`, { headers: { ...headers, "x-api-key": key, ... } })
```

- `AI_GATEWAY_BASE_URL` unset: Anthropic's origin and no extra header, so nothing changes until the gateway exists. Set:
  the gateway's Anthropic endpoint, `https://gateway.ai.cloudflare.com/v1/{account_id}/{gateway_id}/anthropic`. A value
  that is not https or does not end in `/anthropic` throws.
- The site's own Anthropic key stays the credential; the gateway stores none.
- `AI_GATEWAY_TOKEN`, when set, goes as `cf-aig-authorization: Bearer ...`, which an authenticated gateway requires.
- `cf-aig-collect-log-payload: false` keeps request and response bodies out of the gateway's logs (the metadata log of
  model, tokens, cost and status stays), and `cf-aig-metadata: {"app": ..., "feature": ...}` names the site (and, when
  `anthropicRoute(env, app, feature)` is given one, the feature) on every log entry, so one gateway serves every site.
- `gatewayId` is the id in a standard gateway URL, else `AI_GATEWAY_ID`, else null (a custom domain names no id).

## The Anthropic caller

`./anthropic` is the family's one Messages caller, raw fetch over `anthropicRoute`, so a site writes its prompt and
nothing else.

```js
import { messages, stream, structured, untrusted, UNTRUSTED_DATA_RULE } from "@dustinedwards/site-runtime/anthropic";
const answer = await messages(env, "example", { model, max_tokens: 800, system, messages: [...] }, { feature: "summary" });
if (!answer.ok) return fallback(answer.kind); // FAILURE_TEXT[answer.kind] is safe to show a reader
const parsed = await structured(env, "example", request, schema, { feature: "recommendations" });
for await (const event of stream(env, "example", request)) { /* { type: "text", delta } ..., then { type: "done", result } */ }
const prompt = `${UNTRUSTED_DATA_RULE}\n${untrusted("email", customerText)}`;
```

- One deadline per call (`timeoutMs`, default 60 s), retries and their waits inside it. One retry layer, here: 429 with
  `retry-after`, 500, 504, 529 and network errors, with backoff, at most 3 attempts. A spend-cap 429, a 429 without
  `retry-after`, the spend-limit 400 and every other 4xx are never retried. The gateway's own retries stay off.
- A stop that is not an answer is a typed failure, never text: `max_tokens` (`truncated`), `refusal`,
  `model_context_window_exceeded`, an unknown stop; `pause_turn` is resent up to `maxPauses`. `max_tokens` is required, and
  `temperature`, `top_p` and `top_k` throw: `anthropic-version` is `2026-10-21`, which refuses them.
- Prompt caching is on by default once the system prompt reaches the model's minimum (`cache: false` turns it off),
  unless a block already carries its own `cache_control`: the caller's breakpoints are then sent as written.
- One `anthropic_call` log line per call through `./log`: model, stop reason, request id, gateway log id, tokens and
  duration, never the prompt or the answer. `onResult(record)` hands the same record to a site's meter, for a stream
  the reader left early (`aborted`) and a `structured` reply that did not parse (`invalid_output`) too.
- `MODELS` holds each model the family uses with its retirement date from Anthropic's deprecations page, and
  `modelStatus(id)` answers `ok`, `retiring` (within 60 days), `retired` or `unknown` for the live check.
- `untrusted(label, text)` wraps outside text as `<data label>` with `&`, `<` and `>` escaped, so it cannot close its tag.

## Sign-in

`./sign-in` is the one way a person signs in to any family site, chosen 2026-10-24 from current practice: a passkey
first, an emailed link before a passkey exists, Google and Apple only on a consumer app. Admins are not here; they come
through Cloudflare Access (`./access`).

```js
import { signInOptions, signInMethods } from "@dustinedwards/site-runtime/sign-in";
const auth = betterAuth({
  baseURL: env.BETTER_AUTH_URL,
  secret: env.BETTER_AUTH_SECRET,
  database: drizzleAdapter(db, { provider: "sqlite", schema }),
  ...(await signInOptions(env, {
    siteName: "Example Co", sendMagicLink, social: true, emailLimiter: env.AUTH_RATE_LIMITER, eventsDb: env.DB,
  })),
});
// the confirm page's action (CONFIRM_PATH, /sign-in/confirm): return confirmSignInLink(auth, request)
// the confirm page's loader: signInLinkProblem(request.url, { signedIn }) -> null | "used" | "expired" | ... (SIGN_IN_LINK_WORDS)
// the email-change mails: url: emailConfirmURL(url) (EMAIL_CONFIRM_PATH, /email/confirm); its action: confirmEmailLink(auth, request)
// the email-change page: emailLinkResult(request.url) -> { done, problem }
// where and when each session was last used: signInOptions(env, { ..., sessionDetails: true }) with SESSION_DETAILS_SQL
// the sign-in page's loader: signInMethods(env, { social: true }) -> { google, apple, turnstileSiteKey }
// the browser: createAuthClient({ plugins: signInClientPlugins() }) from "@dustinedwards/site-runtime/sign-in-client"
// sendMagicLink({ email, url, token, code }) mails the link and the code together
// a phone app: signInOptions(env, { ..., appCode: true, sendSignInCode: ({ email, code }) => mailCode(email, code) })
// a site's own export or delete route: await requireFreshSession(auth, request) (throws SESSION_NOT_FRESH when stale)
// a person's security history: await securityHistory(env.DB, user.id)
// the account page's passkeys: await accountPasskeys(auth, request, env.DB) -> [{ id, name, provider, createdAt, lastUsedAt }]
// after a sign-in by link, code or Google: await shouldOfferPasskey(env.DB, user.id, passkeys), and canOfferPasskey() in the browser
```

- Passkey: its relying party is the host of `BETTER_AUTH_URL`, so a passkey made on the live site works there only. The
  site needs the plugin's `passkey` table, and the `passkey` opt-in in its registry entry (`buildSecurityHeaders({ site: entry })`, which applies `PASSKEY_OVERRIDES`):
  OSHP's Permissions-Policy turns passkey sign-in off (`publickey-credentials-get=()`). A new passkey is made with
  `authenticatorSelection: { residentKey: "required", userVerification: "preferred" }` (the passkey plugin's option,
  spread over its defaults `preferred`/`preferred`), so it is discoverable: it signs in from the browser's list with no
  email typed. Attestation stays `none` and the person's existing passkeys are excluded, as the plugin does.
- Email link and code: one mail, sent by the site's `sendMagicLink({ email, url, token, code })`, carries Better
  Auth's magic link and a six-digit code (its email OTP). The link signs in the browser that opens it, often the mail
  app's rather than the tab that asked (a private window, a phone); the code, posted as `{ email, otp }` to
  `SIGN_IN_CODE_PATH` (`/sign-in/email-otp`), signs in the tab that asked. Both work once and last
  `SIGN_IN_EXPIRES_IN_SECONDS` (10 minutes, NIST SP 800-63B-4's limit for an out-of-band sign-in;
  `SIGN_IN_EXPIRES_IN_WORDS` for the mail; Better Auth's default 5 ran out in Foxhound's live test). The link's token and the code are stored hashed (the magic link's `storeToken: "hashed"`,
  SHA-256; the email OTP's `storeOTP: "hashed"`), so a read of the `verification` table signs nobody in. Three wrong
  tries spend a code, and the wrong ones also count against the address across links (`CODE_EMAIL_RULES`, below), so
  a new link brings a new code but no fresh tries. Only the link request mails: the email OTP's own endpoints are in `disabledPaths`, so Turnstile
  and the link's limit cover every sign-in mail. Capsomer 0.40.0's `magicLink` template takes the `code`. Passwords
  are off.
- The link opens a page; only its button signs in. Better Auth's link is `GET /api/auth/magic-link/verify`, which signs
  in on the GET, so a mail scanner that opens every link (Microsoft Defender's Safe Links, Mimecast, Proofpoint) spends
  it or signs itself in. The mailed `url` is instead the site's own page, `confirmPath` (default `CONFIRM_PATH`,
  `/sign-in/confirm`), with the link's `token` and `callbackURL` (and `newUserCallbackURL`, `errorCallbackURL` when set)
  in its query. A site adds that one route: a page with one POST button and an action that returns
  `confirmSignInLink(auth, request)`. The helper runs Better Auth's verify through `auth.handler`, so its limits run (the
  magic link's five a minute per IP, keyed on `cf-connecting-ip`, which it passes on), and returns Better Auth's answer
  untouched: a 302 to `callbackURL` with the session's `Set-Cookie`, a 302 to `errorCallbackURL` (else `callbackURL`)
  with `?error=INVALID_TOKEN` for a spent, expired or unknown token, or 429. It reads the parameters from the POST's
  URL (a form with no `action` posts to the page's own URL, query and all), else from the form's fields; anything but a
  POST is 405, and no token is 400. With no `callbackURL` it sends `/`, since Better Auth answers a verify without one
  with the session token as JSON. The page sends `Cache-Control: no-store` and `noindex`, loads nothing from another
  origin (its URL holds the token; a sign-in site's `Referrer-Policy: strict-origin-when-cross-origin`, in `./sites`,
  gives another origin the origin alone, while OSHP's `no-referrer` would make the button post `Origin: null`, which
  React Router and Better Auth refuse with a 400), and says
  what pressing does: "Sign in to {site}". Better Auth's GET endpoint stays as it is (`confirmSignInLink` calls it), but
  no mail carries it.
- What the confirm page says when the link failed (E6): Better Auth answers `?error=INVALID_TOKEN` for a used link and an
  expired one alike, so the mailed URL carries `sent`, the time it was mailed (`confirmLinkURL`), and
  `confirmSignInLink` carries it to `errorCallbackURL` (the confirm page itself when the site names none), txasm's way.
  The page's loader calls `signInLinkProblem(request.url, { signedIn })`: null (show the button), `"used"` (within
  `SIGN_IN_EXPIRES_IN_SECONDS` of the mail), `"expired"` (after), `"invalid"` (no send time: a link cut or edited, or
  mailed before 0.59.0), `"missing"` (no token: cut short when copied), `"failed"` (any other error), or `"signed-in"`
  (this browser is signed in, so nothing more to do). `SIGN_IN_LINK_WORDS[problem]` is `{ title, text }` in the
  network's words; a site may use its own.
- The email change's links open a page too (E1). Better Auth's `/verify-email` link acts on a GET (it approves the
  change from the current address, and makes it from the new one), so both mails carry the site's own page instead:
  `emailConfirmURL(url, confirmPath = EMAIL_CONFIRM_PATH)` in `user.changeEmail.sendChangeEmailConfirmation` and in
  `emailVerification.sendVerificationEmail`, from the `url` Better Auth hands each (only the token is carried). The page
  shows one button; its action returns `confirmEmailLink(auth, request, { callbackURL })`, which runs `/verify-email`
  through `auth.handler` and answers with Better Auth's redirect to `callbackURL` (the page itself by default) with
  `done=approved` (the current address approved; the new one is mailed), `done=changed` (the change is made, with the
  session cookie for a browser that was signed out) or `error=`. GET is 405, no token 400. The page's loader reads
  `emailLinkResult(request.url)`: `{ done }`, or `{ problem }` (`"expired"`, `"done"` for a change made already,
  `"other-account"` when this browser is signed in to another account, `"invalid"`, `"failed"`, `"missing"`).

  ```tsx
  // app/routes/email.confirm.tsx (React Router): one route for both links.
  export const headers = () => ({ "Cache-Control": "no-store", "X-Robots-Tag": "noindex" });
  export const loader = ({ request }: Route.LoaderArgs) => emailLinkResult(request.url);
  export async function action({ request, context }: Route.ActionArgs) {
    return confirmEmailLink(await getAuth(context.cloudflare.env), request);
  }
  // sendChangeEmailConfirmation: ({ user, newEmail, url }) => mail(user.email, emailConfirmURL(url))
  // sendVerificationEmail: ({ user, url }) => mail(user.email, emailConfirmURL(url))
  ```

  ```tsx
  // app/routes/sign-in.confirm.tsx (React Router). The page shows a button; a GET never signs in.
  import { confirmSignInLink } from "@dustinedwards/site-runtime/sign-in";
  export const headers = () => ({ "Cache-Control": "no-store", "X-Robots-Tag": "noindex" });
  export async function action({ request, context }: Route.ActionArgs) {
    return confirmSignInLink(await getAuth(context.cloudflare.env), request);
  }
  export default function Confirm() {
    return <Form method="post"><button type="submit">Sign in to Example Co</button></Form>;
  }
  ```
- Per address, as well as per IP: with `emailLimiter` (the site's `RateLimiter` Durable Object namespace,
  `./rate-limit`), each address gets five sign-in mails an hour (`LINK_EMAIL_RULES`: the link request, and with
  `appCode` the app's code request); three wrong codes an hour and ten a day, counted across links
  (`CODE_EMAIL_RULES`: `SIGN_IN_CODE_PATH`); and ten failed passkey or social sign-ins an hour (`SIGN_IN_FAILURE_RULES`:
  the passkey's owner, the address in an app's ID token, or for a web Google or Apple sign-in the address the provider
  answered the callback with (F1): the providers' `mapProfileToUser` notes it, a failed callback counts against it, and
  once it is spent the next callback goes back to the sign-in's error page with `?error=EMAIL_RATE_LIMITED` before any
  account is read; before the provider answers, only the per-IP limit holds a callback). Each passkey gets 100 failed sign-ins in 30 days (`PASSKEY_FAILURE_RULES`, by credential id; NIST
  SP 800-63B-4's cap per authenticator). The per-IP limits do nothing against someone spread over many addresses
  aiming at one inbox, to bomb it with mail or to guess its code: three wrong tries spend a code, and a new link brings
  a new code but no fresh tries. Mails are counted when asked for; codes, passkeys and social sign-ins are checked
  before (a peek that counts nothing, `./rate-limit`) and counted only when they fail, so signing in right costs
  nothing. These are a plugin's before and after hooks, so a POST straight to `/api/auth` and a form's `auth.api` call
  spend the same budget; on a request to `/api/auth` they run after Turnstile and Better Auth's per-IP limit (both run
  on the request, before any hook), so a request without a Turnstile pass spends nothing. The keys are
  `emailKey("link-email" | "code-email" | "sign-in-fail" | "passkey-fail", ...)` (`./rate-limit`): a SHA-256 of the
  address trimmed and lower-cased (or of the credential id), so the counter never holds the address; the first two are
  Foxhound's, so its counts carry over. A refusal is Better Auth's error shape, 429 with `Retry-After` and `code:
  "EMAIL_RATE_LIMITED"`. A failing counter lets a mail, a passkey or a social sign-in through (`onUnavailable:
  "allow"`, logged as one line naming the bucket only), as Foxhound's did: a Durable Object hiccup must never lock a
  person out. A typed code fails closed: with the counter down, or with no `emailLimiter` at all, `SIGN_IN_CODE_PATH`
  answers 503 `RATE_LIMIT_UNAVAILABLE`, because the code is the one thing a guesser can try a million of; the link in
  the same mail still works.
- Session length: `session.expiresIn` is `SESSION_SECONDS` (30 days, NIST SP 800-63B-4's overall timeout at AAL1)
  with `disableSessionRefresh`, so a session ends 30 days after its sign-in however often it is used (Better Auth's
  default is 7 days sliding forward with each use, which never ends a session in use). Admin pages are behind
  Cloudflare Access, whose session (24 hours by default) is the admin's limit.
- Fresh sign-in (A7, D6): `session.freshAge` is `FRESH_SECONDS` (10 minutes; Better Auth's default is a day). Better
  Auth 1.7.12 then answers 403 `SESSION_NOT_FRESH` unless the session was made in the last 10 minutes on: adding a
  passkey (`/passkey/generate-register-options`, `/passkey/verify-registration`), unlinking Google or Apple
  (`/unlink-account`) and listing sessions (`/list-sessions`), all through its `freshSessionMiddleware`; and deleting the
  account (`/delete-user`, its own check, 400 `SESSION_EXPIRED`, when no deletion mail is set). Better Auth leaves
  removing a passkey (`/passkey/delete-passkey`) and changing the email (`/change-email`) out, so the account plugin's
  before hook holds them to the same rule with the same answer, 403 `SESSION_NOT_FRESH` (logged as `authz_fail`).
  Renaming a passkey and revoking sessions stay open. A site's own risky routes, such as exporting or deleting an
  account outside Better Auth, call `requireFreshSession(auth, request)`: the session when it is fresh, null when
  nobody is signed in, and a throw of `SessionNotFresh` (403, `body.code: "SESSION_NOT_FRESH"`, Better Auth's shape)
  when it is older. A page that gets `SESSION_NOT_FRESH` asks for a new sign-in. A site that sets its own
  `session` options keeps this one: `session: { ...signIn.session, expiresIn, updateAge }`. Session lengths are the
  site's for now.
- Session details (D5, E4), when the site passes `sessionDetails: true`. Each session keeps its coarse place
  (`coarseLocation` of `request.cf`, "Austin, Texas, United States") and a device id: a random value in a signed cookie
  (`DEVICE_COOKIE`, `__Secure-better-auth.device` on https, HttpOnly, SameSite=Lax), set at each sign-in and kept 400
  days, stored on the session row and, with `eventsDb`, on each sign-in's `auth_events` row. Both are written when the
  session is made (a database hook). When the session is read through `/get-session` (the browser's `useSession`, or
  the site's `auth.api.getSession`), its `updatedAt` moves, and its place fills in or follows the person, at most every
  `SESSION_TOUCH_SECONDS` (five minutes; `sessionTouch`, txasm's touch), after the answer through
  `runInBackgroundOrAwait`. So `lastActiveAt` in the sessions list is when it was last used, not when it signed in
  (refresh is off, so nothing else moves `updatedAt`; freshness counts from `createdAt`, so a touch never makes a
  sign-in fresh). The place comes from the request's `cf`, so a site's own server-side read passes the request too:
  `auth.api.getSession({ headers: request.headers, request, asResponse: false })`. A failed write is logged
  (`session_touch_failed`) and never fails the read. The site adds `SESSION_DETAILS_SQL` (`ALTER TABLE session ADD
  COLUMN location TEXT; ... device_id TEXT`, leaving out a column it has) and, with `eventsDb`, `AUTH_EVENTS_DEVICE_SQL`;
  in a Drizzle schema the session table gains `location: text("location")` and `deviceId: text("device_id")`. The
  device id is never sent to a browser (`returned: false`). A site that kept its own touch or place hook drops it.
- Sign-out clears the browser: Better Auth's `/sign-out` (which deletes the session row and its cookie) answers with
  `LOGOUT_HEADERS` (`./headers`: `Clear-Site-Data: "cache","cookies","storage"`). It is a plugin's after hook, not the
  options' `hooks.after`, so a site with an after hook of its own keeps both with nothing to merge. Browsers apply
  `"cookies"` to the whole registrable domain, so signing out of a site on a subdomain of dustinedwards.info clears the
  cookies of its sibling subdomains too.
- What the mail must carry: `sendMagicLink({ email, url, token, code })` gets the confirm page's link (`url`, which
  holds `token`) and the six-digit `code`. The mail carries both, the link untouched and the code as text, and says they
  last `SIGN_IN_EXPIRES_IN_WORDS`. A mail without the code leaves the tab that asked with nothing to type. Neither is ever
  logged: each signs in, so a send error has `url`, `token` and `code` cut out (Foxhound's `send-auth-email.ts`).
- A phone app's code: `appCode: true` with `sendSignInCode({ email, code })`. An app cannot open the link (it opens in
  the phone's browser) or show the Turnstile widget, so it asks for a code alone at `APP_CODE_PATH`
  (`/email-otp/send-verification-otp`) and signs in at `SIGN_IN_CODE_PATH`. That one path comes off `disabledPaths`;
  the rest stay off. It is the same plugin's code (sign-in only, hashed, three tries, `SIGN_IN_EXPIRES_IN_SECONDS`), and
  only a sign-in code is mailed: a request for any other kind mails nothing. With no Turnstile in front of it, it is
  held to three a minute (`APP_CODE_RATE_LIMIT`, in `rateLimit.customRules`). A site that spreads its own `rateLimit`
  keeps `...signIn.rateLimit`. This replaces a second `emailOTP` plugin beside the shared one (Foxing's), which does
  not work: the shared `disabledPaths` turn its send path off (404), and Better Auth 1.7.12 logs an endpoint conflict.
- No OAuth tokens: with `social: true` the options carry `databaseHooks.account`, which blank Google's and Apple's
  access, refresh and ID tokens on every account write Better Auth makes (createOAuthUser, linkAccount, updateAccount).
  Nothing in sign-in reads them, so none are stored. A site with hooks of its own merges them:
  `databaseHooks: { ...signIn.databaseHooks, user: { ... } }`.
- Turnstile checks the email link when `TURNSTILE_SITE_KEY` and `TURNSTILE_SECRET_KEY` are both set. Without both,
  it fails closed: `/sign-in/magic-link` (the one request that mails the link and its code) answers 503
  `TURNSTILE_NOT_SET` and logs `turnstile_not_set`. A site whose keys are not made yet passes
  `turnstile: "off-until-keys"` (`TURNSTILE_OFF_UNTIL_KEYS`), which lets the request through unchecked and logs
  `turnstile_off_until_keys` (warn) on every one, so the gap shows in the logs until the keys are set and the option
  comes out. It must be written on purpose: any other value throws. The app's code request (`appCode`) has no widget
  and stays outside Turnstile, held to three a minute.
- An email change or a recovery ends every other session (D7): after a verified change of address, and after a
  recovery (below), every session of that person but the one that made it is deleted (`session_expired`, `reason:
  "email_changed"` or `"recovered"`, `scope: "others"`). Deleting the account deletes them all (Better Auth).
- Google (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) and Apple (`APPLE_CLIENT_ID`, the Services ID; `APPLE_TEAM_ID`,
  `APPLE_KEY_ID`, `APPLE_PRIVATE_KEY`, the .p8 text) when the site passes `social: true` and has the settings.
  `./apple-secret` signs Apple's client secret, a JWT Apple refuses after six months, fresh from the key in each isolate.
- Accounts are joined only by a signed-in person (`linkSocial`), never by a matching email at sign-in.
- Rate limited in the database, keyed on `cf-connecting-ip`, in every environment. Sessions and the counts live in the
  site's D1 (`session`, `rateLimit`), never KV, which is eventually consistent.
- Async, because Apple's secret is signed with WebCrypto: a site keeps the promise per isolate.

### Account security: the event log, notices, sessions and passkeys

`sign-in-account.mjs`, re-exported by `./sign-in` and run from a plugin's hooks, so a site gets the log with no code of
its own and the notices by passing one function.

- The auth event log (F2): one `./log` line per event, named from the OWASP Logging Vocabulary (`OWASP_EVENTS`).

  | Event | Line |
  | --- | --- |
  | sign-in, by `via`: `link`, `code`, `passkey`, `google`, `apple` | `authn_login_success` (`user_id`), `authn_login_fail` (`code`, such as `INVALID_TOKEN`, `INVALID_OTP`, `PASSKEY_NOT_FOUND`) |
  | a sign-in link or the app's code mailed | `authn_token_created` (`via`) |
  | a per-address limit hit (`emailLimiter`) | `excess_rate_limit_exceeded` (`endpoint`, `bucket`) |
  | sign-out | `session_logout` |
  | a session ended from the sessions list | `session_expired` (`reason: "revoked"`, `scope`: `one`, `others`, `all`) |
  | a passkey added or removed, Google or Apple linked or unlinked, the email changed, a recovery | `user_updated` (`change`: `passkey_added`, `passkey_removed`, `sign_in_linked`, `sign_in_unlinked`, `email_changed`, `recovered`) |
  | the other sessions ended after an email change or a recovery | `session_expired` (`reason`: `email_changed`, `recovered`; `scope: "others"`) |
  | the account deleted | `user_deleted` |
  | refused for want of a fresh sign-in | `authz_fail` (`reason`: `SESSION_NOT_FRESH`, or `/delete-user`'s `SESSION_EXPIRED`; `endpoint`) |

  A line carries `user_id` once there is a user, and before that the address hashed as `emailKey` hashes it
  (`email_key: "email:<sha-256>"`); never the address, a token, a code or a session id. Better Auth's own per-IP limits
  answer 429 before any hook runs (its router's `onRequest`), so those refusals are not in the log; Workers Logs shows
  them as 429s on `/api/auth`.
- Security notices (A8, E1; NIST SP 800-63B-4 4.1.2.1 and 4.6): `signInOptions(env, { ...,
  sendSecurityNotice })` calls `sendSecurityNotice(kind, { user, request, detail })` for `passkey-added`,
  `passkey-removed`, `sign-in-linked`, `sign-in-unlinked`, `email-changed` (twice, once to each address, the old one
  told to get in touch), `sessions-revoked` (every session, or every other one: `detail.scope`), `account-deleted`,
  `new-device` (E3: a sign-in from a device the person has not signed in from, among their other sessions and, with
  `eventsDb`, their history; a first sign-in is not one. With `sessionDetails`, a device is its device id, so a second
  Mac running Chrome is new, and so is a browser that signed out or cleared its cookies, since Clear-Site-Data removes
  the cookie; until a person has a device id on record, and without `sessionDetails`, a device is its `deviceName`) and `recovery` (E4: a sign-in by link or
  code with no passkey left, by someone whose history shows a passkey added, so it needs `eventsDb`; the notice says
  every other device was signed out and to add a passkey, which the page then offers) (`SECURITY_NOTICE_KINDS`). `user.email` is where it goes. `detail` is the words: `title` (the subject), `what`,
  `when` (UTC, in words) and `at`, `device` ("Safari on iPhone") and `location` ("Portland, Oregon, United States", from
  `request.cf`; null for a request a site built itself, as `confirmSignInLink` and `auth.api` calls are), and `secure`,
  what to do if it was not them. Capsomer's `securityNotice` mail takes it as it is:

  ```js
  sendSecurityNotice: async (kind, { user, detail }) => {
    const { subject, html, text } = renderEmail(securityNotice, { brand, to: user.email, ...detail, url: `${origin}/account` });
    await sendMail({ to: user.email, subject, html, text }); // the site's own sender
  },
  ```

  A send that throws is logged (`security_notice_failed`, the kind and the error with any address cut out) and the
  change stands: every hook catches its own error (`auth_event_failed`), because a throw from an after hook would turn
  a change already made into an error answer. The send goes through Better Auth's `runInBackgroundOrAwait`, so with
  `advanced: { ...signIn.advanced, backgroundTasks: { handler: (p) => ctx.waitUntil(p) } }` the answer does not wait
  for the mail. A linked or unlinked provider, the two addresses of an email change and a deleted user's address come
  from database hooks (the plugin's own, beside the site's `databaseHooks`); the email change is caught on both of
  Better Auth's paths, `/change-email` for an unconfirmed address and `/verify-email` for a confirmed one.
- Security history (E5): with `eventsDb` (the site's D1, with `AUTH_EVENTS_SQL` as its next migration), every line
  above is also a row in `auth_events`: the time, the OWASP event, its `change` or `scope`, the way in, the user's id
  when there is one, and the device and coarse place; never an address, token or code. `securityHistory(db, userId,
  limit = 50)` gives a person's own sign-ins, passkey and sign-in method changes, email changes and recoveries, newest
  first, as `{ kind, via, at, device, location }` for a page to show. Deleting the account deletes that person's rows.
  `pruneAuthEvents(db)` is a daily job (`./cron`): rows with no user go after 30 days, the rest after a year. A failed
  write is logged (`auth_event_write_failed`) and never stops a sign-in. `./health`'s `authSpikeCheck` reads the same
  table.
- Sessions list (D5): `await accountSessions(auth, request)` gives `{ id, device, signedInAt, lastActiveAt, current,
  location }` rows (`sessionRows` over Better Auth's `listSessions`), the current session first, or null when
  `/list-sessions` wants a fresh sign-in (SESSION_NOT_FRESH), so the page offers "sign in again" instead of failing.
  `device` is `deviceName(userAgent)`, a small parser of the browser and system (Edge, Opera, Samsung Internet,
  Firefox, Chrome, Safari; iPhone, iPad, Android, ChromeOS, Windows, Mac, Linux), null when the agent names neither.
  `lastActiveAt` is `updatedAt`: with `sessionDetails`, when the session was last used (within five minutes); without
  it, the sign-in time, since refresh is off. Better Auth stores the address and the user agent, not a place, so
  `location` is null unless `sessionDetails` (or the site) keeps one on the session. A row carries no token: the rows go into the page, and another device's token there would
  let a script on the page take over that session. Ending one is the page's own action calling
  `revokeSessionById(auth, request, id)` (Better Auth's `/revoke-session`, server-side; false when the id is not the
  asker's); every other is `/revoke-other-sessions`; all, `/revoke-sessions`.
- Passkey names (A5): a passkey registered with no name is stored with its provider's, from its AAGUID
  (`knownProvider`: the passkey-authenticator-aaguids list trimmed to the password managers people use, by that list's
  names: "Apple Passwords", "Google Password Manager", "Windows Hello", "1Password" and so on, plus the retail YubiKey 5
  models from the FIDO Metadata Service; names only). Apple's own passkeys report the all-zero AAGUID when no
  attestation is asked for, so a zero from an iPhone, iPad or Mac reads as Apple Passwords. It is the passkey plugin's
  `registration.afterVerification`, whose name a name the page sends overrides; an unknown provider leaves the name
  blank. `passkeyProvider(aaguid)` is the same for a page, "Passkey" when unknown, and `passkeyLabel(passkey)` is what
  a list shows: the name, else the provider.
- The passkey list (A5): `await accountPasskeys(auth, request, env.DB)` gives the asker's passkeys, oldest first, as `{
  id, credentialId, name, provider, createdAt, lastUsedAt }` (`passkeyRows` over Better Auth's `listPasskeys`; the
  public credential id for the Signal API, no public key), or null when nobody is signed in. Better Auth 1.7.12 keeps no last-used time, so with `eventsDb` each
  passkey sign-in's `auth_events` row carries the passkey's id in `change`, and `passkeyLastUsed(db, userId)` reads the
  newest per passkey: no migration beyond `AUTH_EVENTS_SQL`. Rows go after a year, so a passkey unused that long shows
  no date, and passkeys used before this version show none until their next sign-in. Rename is Better Auth's own
  `authClient.passkey.updatePasskey({ id, name })`; adding another is `authClient.passkey.addPasskey()`; delete is
  `authClient.passkey.deletePasskey({ id })`. Listing and renaming need no fresh sign-in; adding and deleting do
  (FRESH_SECONDS), so the page offers "sign in again" on SESSION_NOT_FRESH.
- The passkey offer (A3): after a sign-in by link, code, Google or Apple, the page the sign-in lands on asks
  `await shouldOfferPasskey(env.DB, user.id, passkeys)`: true when the person has no passkey and has not said "Not
  now" in the last `PASSKEY_OFFER_DAYS` (30). If so it shows one screen offering a passkey, and in the browser skips
  it when `await canOfferPasskey()` (`./sign-in-client`, the platform authenticator check) is false. "Not now" posts
  to the page's own action, which calls `dismissPasskeyOffer(env.DB, user.id, { request })`. The dismissal is an
  `auth_events` row (`passkey_offer_dismissed`), so it belongs to the person rather than one browser, needs no other
  table, and is not in the security history; it needs `eventsDb`.
- Two ways in (A9): `needsSecondPasskey(rows)` is true with exactly one passkey; the account page then suggests adding
  another on a second device.
- The WebAuthn Signal API (A6), in `./sign-in-client`. Each call runs only where the browser has it (Chrome 132,
  Safari 26) and swallows a refusal; `rpId` defaults to the page's host. When a site calls each:

  | Call | When |
  | --- | --- |
  | `signInWithPasskey(authClient, { autoFill })` | every passkey button and autofill, in place of `authClient.signIn.passkey(...)`: on `PASSKEY_NOT_FOUND` (deleted elsewhere) it signals that credential unknown, and on success it keeps the passkey's user handle (`passkeyUserHandle()`) for the calls below |
  | `signalPasskeys({ credentialIds, name, displayName })` | after a passkey sign-in lands, and each time the account page's passkey list loads, with the rows' `credentialId`s and the account's address as `name` |
  | `signalCurrentUserDetails({ name, displayName })` | after the email change is made (on the page `emailLinkResult` says `done: "changed"`, `name` the new address) and after the person renames themselves |
  | `signalAllAcceptedCredentials({ credentialIds })` | inside `signalPasskeys`; alone where only the list matters |
  | `signalUnknownCredential({ credentialId })` | after the person deletes a passkey on the site, with that row's `credentialId` |

  `userId` is a passkey's user handle, and @better-auth/passkey 1.7.12 makes a new random handle for every passkey and
  stores none (`generate-register-options`), so the one handle a page can know is that of the passkey that signed in
  on this browser (`webauthn.response.response.userHandle`), which `signInWithPasskey` keeps in localStorage per relying
  party; a page may pass `userId` itself. Without one the calls do nothing, and they reach that passkey alone. A
  deleted passkey is therefore signaled by its id, with `signalUnknownCredential`.

## The live sign-in check

`site-runtime-sign-in --origin https://example.com [--from https://example.workers.dev]` (`bin/sign-in.mjs`, logic in
`sign-in-live.mjs`) is the daily live check for sign-in and access (devkit `live/areas.json`, area 3). It sees what an
outside request can: it sends no mail, makes no account and holds no token, and each part runs only when the site has it.

- Sign-in page (`/login`, `/signin`, `/sign-in`): `no-store` and `noindex` (D10), an email field whose autocomplete has
  `webauthn` (A2; a warning when it does not start with `username`), Turnstile on the page and allowed by the CSP (B5).
- Better Auth (`/api/auth/ok`): the passkey's `rpId` is the site's host, not a workers.dev one (A1); sign-out sends
  `Clear-Site-Data` (D4); a sign-out from another origin with a cookie is 403 (D8); every cookie set is `__Secure-` or
  `__Host-`, HttpOnly, Secure and SameSite (D1); each answer is `no-store` (D10). The confirm page with a made-up token
  must never set a session cookie (B7): the site's own path, the first that answers among `/confirm` beside each sign-in
  page found and `/sign-in/confirm`, `/signin/confirm` (txasm's), `/login/confirm`. A missing confirm page is a warning
  until every site has the route.
- Admin (`/admin`, and the pages the site's registry entry names in `signIn.admin`, `./sites`: dustinedwards.info's
  `/lab`, txasm's `/admin/access`, all of Desk and the Portal): a request with no sign-in gets a redirect to
  `*.cloudflareaccess.com` or a 401/403, never the page (G1; another redirect is a warning), with `no-store` and, on
  anything but a redirect, `noindex` (D10). A declared page that answers 404 or 5xx is an error, not skipped.
- MCP (`/mcp`, and the servers the entry names in `signIn.mcp`, such as Foxhound's merchant and admin servers): the
  401 names its `resource_metadata` and that metadata names the
  server and its authorization server (H1, RFC 9728); the authorization server offers PKCE `S256` only (H2) and Client
  ID Metadata Documents (H4), per the MCP authorization spec of 2025-11-25.

Findings print as `::error title=<item>::<url> <detail>` (cookie names, never values); exit 0 clean, 1 on an error, 2
when the site does not answer. `test/sign-in-live.test.mjs` plants each gap in a fake site.

## The Turnstile widget

`./turnstile` loads Cloudflare Turnstile, the bot check on a public form that sends email, so no site keeps its own copy.

```js
import { TURNSTILE_ORIGIN, mountTurnstile } from "@dustinedwards/site-runtime/turnstile";
// The CSP sources: { script: [TURNSTILE_ORIGIN], frame: [TURNSTILE_ORIGIN] }
useEffect(() => mountTurnstile(ref.current, siteKey), [siteKey]);
```

- The script loads once per page (`render=explicit`, so it never renders a widget of its own), and a load that fails is
  tried again on the next mount. The returned function removes the widget; called before the script loads, nothing renders.
- The widget is Cloudflare's flexible size: it fills the element's width (300px at least), so it lines up with the form's
  inputs and buttons.
- The widget leaves its token in a hidden `cf-turnstile-response` input inside the element, so the form sends it with its
  fields. `{ onToken }` is for a form that sends it another way, such as Better Auth's `x-captcha-response` header.
- Browser only. The token is checked on the server, by `./sign-in`'s captcha plugin, or for any other form by
  `verifyTurnstile`.

```js
import { verifyTurnstile } from "@dustinedwards/site-runtime/turnstile";
const check = await verifyTurnstile(form.get("cf-turnstile-response"), env.TURNSTILE_SECRET_KEY, {
  remoteIp: request.headers.get("cf-connecting-ip"),
  hostname: url.hostname,   // optional: the widget ran on this site
  action: "estimate",       // optional: the widget's data-action
});
if (!check.ok) return refuse(check.errors);
```

`verifyTurnstile(token, secret, { remoteIp, hostname, action, timeoutMs })` fails closed and never throws. Only
Cloudflare's `success: true` (with the expected `hostname` and `action`, when given) is `ok: true`. No secret, no token or
one over 2048 characters, siteverify unreachable, slow past `timeoutMs` (10 seconds) or answering an error status or
something that is not JSON: each is `ok: false`, with `errors` holding Cloudflare's codes or one of `missing-secret`,
`missing-input-response`, `siteverify-unreachable`, `not-success`, `hostname-mismatch`, `action-mismatch`. Never wrap it
in a catch that returns a pass.

**Tests.** `test/turnstile.test.mjs`, against a fake document and a fake siteverify.

## Starting a Claude Code routine

`./routine` is how a site starts work on Dustin's Claude subscription: a POST to a routine's API trigger. Anthropic allows
subscription sign-in only in Claude Code and its own apps, so a site that wants model work without an API key starts a
routine, which does the work in Claude Code and hands the result back to the site.

```js
import { fireRoutine, routineConfig } from "@dustinedwards/site-runtime/routine";
const config = routineConfig(env.AI_ROUTINE_URL, env.AI_ROUTINE_TOKEN);
if ("missing" in config) return config.missing;
const fired = await fireRoutine(config, "job: ...");
```

- The URL must be `https://api.anthropic.com/v1/claude_code/routines/trig_.../fire`, so the token only goes to Anthropic.
  The token comes from the routine's API trigger at claude.ai/code/routines and is a Worker secret.
- `fireRoutine` never throws. Its `outcome` is `started` (with `sessionId` and `sessionUrl`), `rate_limited` (429, with
  `retryAfter`), `unavailable` (5xx, retry later), `refused` (4xx, do not retry), `unreachable` (no connection was made)
  or `unknown` (a timeout or dropped answer: the session may exist, so it is never retried).
- Each fire is a new session and the endpoint has no idempotency key, so `fireOnce(store, jobKey, config, text)` records
  each job before it fires and refuses a second fire for the same key unless `force` is set or the record is older than
  `refireAfterMs`. The store needs an atomic `add`, so it is D1 or a Durable Object, never KV (eventually consistent:
  two fires from two locations both read nothing). A reservation older than 10 minutes, left by a worker that died
  mid-fire, is reported as `unknown`: check whether a session started, then `force`.

```js
const store = {
  get: async (k) => (await env.DB.prepare("SELECT v FROM routine_fires WHERE k = ?").bind(k).first("v")) ?? null,
  put: (k, v) => env.DB.prepare("INSERT INTO routine_fires (k, v) VALUES (?, ?) ON CONFLICT (k) DO UPDATE SET v = excluded.v").bind(k, v).run(),
  delete: (k) => env.DB.prepare("DELETE FROM routine_fires WHERE k = ?").bind(k).run(),
  add: async (k, v) => (await env.DB.prepare("INSERT INTO routine_fires (k, v) VALUES (?, ?) ON CONFLICT DO NOTHING RETURNING k").bind(k, v).first()) !== null,
};
const fired = await fireOnce(store, `newsletter:${issueId}`, config, "job: ...");
```

## The cross-site check

`./origin` refuses a cross-site request that changes something, on the routes no framework check covers. React
Router checks the Origin of a document's action, but a resource route (no default export: an API endpoint, a form post
answered with a redirect, an admin JSON route) never reaches that check, and a Worker route outside React Router has
none (dustinedwards.info's admin middleware and theme route).

```js
import { refuseCrossSite } from "@dustinedwards/site-runtime/origin";
const refused = refuseCrossSite(request, SECURITY_HEADERS); // null for GET, HEAD, OPTIONS and a same-origin request
if (refused) return refused;
```

- `refuseCrossSite(request, headers?, { sameSite? })` reads Fetch Metadata first (OWASP CSRF Prevention Cheat Sheet): a
  non-safe method goes on when `Sec-Fetch-Site` is `same-origin` or `none`, or `same-site` with `sameSite: true` (a
  sibling subdomain the site trusts), and is refused for `cross-site`, `same-site` otherwise and any other value. With no
  `Sec-Fetch-Site` (an older browser) it falls back to `originVerdict`.
- `isolationVerdict(request)` is the opt-in resource isolation policy ([web.dev](https://web.dev/articles/fetch-metadata))
  for signed-in routes: `{ ok, reason }`, allowing no Fetch Metadata, `same-origin`, `same-site`, `none`, and a GET
  navigation that is not into an `<object>` or `<embed>`; a cross-site image, script or post is refused. Log what it
  would refuse first, then return `originRefusal` on `!ok`.

- `originVerdict(origin, requestUrl)` is `{ ok, reason }`: an absent Origin passes (`absent`; only non-browser clients
  and a no-script form post omit it, and a hostile page cannot make a browser leave it out), the request's own origin
  passes (`same-origin`), and anything else is refused (`cross-origin`), the string `"null"` of a sandboxed frame
  included. The request's own origin, not a configured one, so the check holds on workers.dev, a preview and the live
  domain alike.
- `originRefusal(headers)` is the 403: `ORIGIN_REFUSAL` as plain text, `no-store`, saying nothing about the route.

## One address per page

`slashRedirect(request, { except })` (`./url`) sends `/x/` to `/x` with its query, so a page is not indexed, cached and
counted twice: 301 for GET and HEAD, 308 otherwise (a form body survives). "/" is never redirected, nor a path in
`except` (exact, or a prefix written with a trailing `*`). The Location is absolute on the request's own origin, so
`//attacker.example/` cannot become a protocol-relative redirect off the site. Null when there is nothing to redirect.

```js
import { slashRedirect } from "@dustinedwards/site-runtime/url";
const redirect = slashRedirect(request, { except: ["/api/*"] });
if (redirect) return redirect;
```

`canonicalRedirect(request, { host, except })` is the whole canonical address in one hop: plaintext to https (not on
localhost), `www.<host>` to `host` when `host` is given, and the trailing slash, so `http://www.example.com/x/` is one
redirect to `https://example.com/x`, never a chain. Sent `private, no-store`: the edge key holds no scheme, so a stored
redirect would loop. Use it first in the gateway in place of separate https, www and slash redirects.

**Pages removed on purpose.** `goneResponse(request, gone)` answers 410 Gone for a path on the site's list, so a
crawler drops it sooner than a 404 and a reader is told it was not a typo. An entry is an exact path, a prefix written
with a trailing `*`, or a RegExp; a trailing slash is ignored. The body is Capsomer's error-page sentence in plain text
unless `body` is given. A site that renders its own 410 page (Capsomer's `ErrorPage` does) tests `pathListed(path, gone)`
in its loader and throws its own 410 instead. Null when the path is not on the list.

```js
import { goneResponse } from "@dustinedwards/site-runtime/url";
const GONE = ["/blog/withdrawn-post", "/old-shop/*", /^\/wp-content\/uploads\/2017\//];
const gone = goneResponse(request, GONE);
if (gone) return gone;
```

**Renamed slugs.** `renameRedirect(request, { prefix, renames })` sends a renamed slug to its new one in one 301 (308
for other methods), keeping what follows the slug and the query: `/blog/old/comments?page=2` to
`/blog/new/comments?page=2`. `renames` is the site's table (old slug to new) or a lookup, sync or async, that returns
null for a slug never renamed, such as a query on a `post_redirects` table. A chain (a to b, b to c) is followed to its
end, so the reader takes one hop, and a loop throws. Sent `private, no-store`, so a rename that is undone is not held in
a browser. It resolves to null when nothing matches; it does not answer React Router's `.data` requests, so a loader
that serves a renamed slug calls it too.

```js
const moved = await renameRedirect(request, { prefix: "/blog/", renames: { "spring-update": "spring-update-2026" } });
if (moved) return moved;
```

## One log line

`./log` writes one JSON line per event, `event` first, so Workers Logs and a tail filter on its name:

```js
import { logEvent } from "@dustinedwards/site-runtime/log";
logEvent("checkout_failed", { path: url.pathname, error }, { level: "error", tokenPath: /\/(u|p|invite)\/[^/?#\s'"]+/g });
// {"event":"checkout_failed","path":"/u/[token]","error":"Error: ..."}
```

Every string field is scrubbed first, with the scrubbers Foxhound's Sentry options used, exported (`scrubText`,
`scrubUrl`, `scrubFields`, `EMAIL_PATTERN`, `STRIPE_KEY_PATTERN`) so a site's error reports cut the same things: email
addresses, a URL's query and fragment (in text, and the whole of a field named for a url or path), Stripe keys, a failed
Drizzle query's bound parameters, and with `tokenPath` the token segment of the site's own routes. Fields named for
headers, cookies, queries or console arguments are dropped; an Error becomes its name and message. The scrubbers are
the net, not the rule: never log a token, a code or a secret on purpose. The package's own lines (`share_card_failed`,
`not_found_count_failed`, `access_keys_unreachable`, `csp_report_unlimited`, `health_check_failed`, the cron lines) go
through it.

`requestFields(request, { sha, status })` is `{ request_id, method, path, status, sha }` to spread into a request's
lines: `request_id` is the `cf-ray` header, so a line matches the request in Cloudflare's logs, and `path` is scrubbed,
never the query.

`withRequestLog(handler, { sha, route })` wraps a fetch handler so every request writes one `request` line: those
fields with the response's status, `route` when `route(request)` names one (the matched pattern, so `/posts/:slug`
groups its hits), and `ms`. A 5xx is logged at error, a 4xx at warn; a throw is logged as 500 and rethrown. `sha` is a
string or a function of the handler's other arguments:

```js
import { withRequestLog } from "@dustinedwards/site-runtime/log";
export default { fetch: withRequestLog(handler, { sha: (env) => env.DEPLOY_SHA }) };
```

`routeNamer(build.routes)` is that `route` for a React Router site: the full pattern of the most specific route in the
build's route table that matches the path (static segments before params, params before a splat; a single-fetch
`.data` request is named as its page). The build is a module the Worker imports, so the namer is made once:

```js
import * as build from "virtual:react-router/server-build";
const route = routeNamer(build.routes);
export default { fetch: withRequestLog(handler, { sha: (env) => env.DEPLOY_SHA, route }) };
```
`OWASP_EVENTS` holds the [OWASP Logging Vocabulary](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Vocabulary_Cheat_Sheet.html)
names for a site's security events: `authn_login_success`, `authn_login_fail`, `authn_token_created`, `session_logout`,
`session_expired`, `user_updated`, `user_deleted`, `authz_fail`, `input_validation_fail` and
`excess_rate_limit_exceeded`. `./sign-in` writes its own events with them (Sign-in, Account security).

## The 404 counter

`./not-found` counts the 404s a site serves, per path, referring host and UTC day, in its D1, so a broken link or a
moved page shows up with where the link to it is: Rank Math's 404 Monitor without its personal data. The table is
`page_404_daily` (`id` a random UUID, `day` UTC midnight in epoch milliseconds, `path`, `referrer_host`, `kind`,
`hit_count`, unique on day, path and referrer host). A new site adds `NOT_FOUND_SQL` as its next migration; a site
with the first shape (no referrer or kind, unique index `page_404_daily_day_path_uq`) adds `NOT_FOUND_UPGRADE_SQL` with
the version that brings it, since the new upsert needs the new key.

```js
import { countNotFound } from "@dustinedwards/site-runtime/not-found";
const response = await handler(request, env, ctx);
countNotFound(env.DB, request, response, ctx); // a 404 to a GET, written in ctx.waitUntil
return response;
```

- Only the pathname, cut to 512 characters (`NOT_FOUND_PATH_MAX`), never the query (it can carry a token). Of the
  Referer only the host of an http or https URL (`referrerHost`), never its path or query; no user agent or address.
  `notFoundKey(url, now)` is the row's `{ day, path, kind }`.
- `kind` is "probe" for a path an exploit scanner guesses, else "page". `NOT_FOUND_PROBE` holds Capsid's traffic
  report's list too: any `/wp-` (`/wp-admin`, `/wp-content`), server scripts (`.php`, `.asp`, `.jsp`, `.cgi`,
  `/cgi-bin/`, `/xmlrpc`), dumps and config (`.sql`, `.bak`, `.env`, `.ini`, `.yml`, `.db`, `/config.json`,
  `/config/`, `env.js`), dotfiles but `/.well-known/`, phpMyAdmin and phpinfo, credential files (`credentials.json`,
  `aws-exports.js`, `appsettings.json`) and AI-key paths (`/openai/`, `/anthropic/`, `/bedrock/`, `/llm/`). A slug
  that only contains a word like "secret" stays a page; only a file name with an extension is a probe.
- GET only. React Router's data request (`/x.data`, `/_.data` for the home page) counts as its page, so a client
  navigation and a document load of the same missing page add to one row.
- One upsert, so two 404s at once cannot both insert or lose a hit. Written in `ctx.waitUntil`, so it never holds or
  fails the response; a failed write is logged (`not_found_count_failed`). `db` may be a function, called inside the
  background write, so a missing binding is logged too. `recordNotFound(db, url, now, referer)` is the awaited write.
- `notFoundReport(db, { days = 30, limit = 50, includeProbes = false })` is the admin screen's list:
  `[{ path, kind, hits, referrers: [{ host, hits }] }]`, most hits first, "" the host for no referrer, probes left out
  unless asked for. `pruneNotFound(db, { days = 90 })` deletes older rows; a site runs it from its cron.

**Tests.** `test/log.test.mjs`, `test/url.test.mjs` (a `//` path stays on the site, the gone list, a rename chain) and `test/not-found.test.mjs` (on
an in-memory SQLite with `NOT_FOUND_SQL`, and with a first-shape table upgraded by `NOT_FOUND_UPGRADE_SQL`).

## Scheduled jobs

`./cron` runs a site's scheduled jobs so that one failure never stops the next, and keeps each job's last start,
success and failure in its D1, so /health can say when a cron failed or stopped. A site adds `CRON_SQL` (`cron_runs`:
name, every_minutes, and the first start, last start, last success, last failure and last error, in epoch
milliseconds) as its next migration.

```js
import { runJobs } from "@dustinedwards/site-runtime/cron";
import { pruneNotFound } from "@dustinedwards/site-runtime/not-found";
async scheduled(controller, env, ctx) {
  await runJobs(env.DB, [
    { name: "backup", everyMinutes: 1440, run: () => runBackup(env) },
    { name: "prune-404", everyMinutes: 1440, run: () => pruneNotFound(env.DB) },
  ]);
}
```

- Each job runs in turn; a throw is logged (`cron_job_failed`, with its name and ms) and stored scrubbed and cut to
  500 characters, and the next job runs.
- Each job has a timeout: its own `timeoutMs`, else `runJobs(db, jobs, { timeoutMs })`, five minutes by default
  (`CRON_TIMEOUT_MS`). A job past it is recorded failed ("timed out after N ms") and the next job starts, so one hung
  job never holds up the rest of its trigger. `run(signal)` gets an AbortSignal that is aborted then, for a job that can
  stop its own work; the runner cannot cancel a promise. A success logs `cron_job_ok`. A failed write to `cron_runs` is logged
  (`cron_run_write_failed`) and the job still runs. After the last job, if any failed, `runJobs` throws one Error
  naming them, so Cloudflare marks the invocation failed. `db` may be a function, like `countNotFound`'s.
- A job holding a lock or moving money sets `holdOnTimeout: true`: past its timeout it is still recorded failed and its
  signal aborted, but the runner waits for it to end before the next job starts (logging `cron_job_overran` then), and
  its late end records no success. Without it, the next job would start beside it and the invocation could end under it.
- A job with a gate of its own (switched off, not due, a lock another run holds) resolves to `CRON_SKIPPED`: it is
  logged `cron_job_skipped` and no success is recorded.
- `cronCheck(db, { jobs, deployedAt, graceMinutes })` is the /health check (name `cron`, level warn): it fails, naming
  the jobs, when a job's last run failed, its last success is older than its own interval plus the grace, or it never
  succeeded and was first started longer ago than that. The grace is `graceMinutes` when given, else the larger of
  10 minutes and a tenth of the interval: 11 minutes for a minutely job, about 26 hours for a daily one. That is how an
  outside probe of /health notices a cron that stopped.
- Pass `jobs` (the same list runJobs gets; `run` is not called) and the check reads only those, with their own
  intervals: a removed job's old row is ignored, and a job with no row at all fails as "never ran" (a trigger that never
  fires it, a misspelt cron key). `deployedAt` (such as `new Date(env.CF_VERSION_METADATA.timestamp)`) holds that back
  until the job's window has passed since the deploy; without it a job that has not run yet warns at once. Without
  `jobs`, a removed job keeps its row, which goes stale: delete the row with the job.
- `cronFindings(db, options)` is the same judgment as data, `[{ name, reason, lastOkAt }]` with reason `failed`,
  `stale`, `never succeeded` or `never ran`, for a site that mails its own alert from it (Foxhound's stale-cron email).

**Tests.** `test/cron.test.mjs` (on an in-memory SQLite with `CRON_SQL`) and `test/health.test.mjs`.

## A constant-time secret compare

`./compare` is the one comparison of a presented secret with the expected one.

```js
import { safeEqual } from "@dustinedwards/site-runtime/compare";
if (!(await safeEqual(presentedToken, env.OPERATOR_TOKEN))) return new Response("unauthorized", { status: 401 });
```

- Both sides are hashed with SHA-256 and the 32-byte digests compared, so neither string's length reaches the compare (the
  hash's own time follows the input's length, which only tells a caller the length of what they sent).
- The digests are compared by `crypto.subtle.timingSafeEqual` where the runtime has it (workerd), and by an XOR over all 32
  bytes where it does not (Node).
- It is async, since WebCrypto's digest is. A side that is not a string, or is empty, matches nothing, so an unset secret
  never admits an absent credential.

## The Access request check

`./access` checks the token Cloudflare Access signs for each request it lets through. It verifies with `./access-login`'s
WebCrypto JWT check (`verifyJwt`, which `verifyIdToken` wraps), so there is no JWT library.

```js
import { verifyAccessRequest } from "@dustinedwards/site-runtime/access";
const verdict = await verifyAccessRequest(request, { teamDomain: env.ACCESS_TEAM_DOMAIN, audience: env.ACCESS_AUD, cookie: true });
if (!verdict.ok) return refuse(verdict.reason);
const email = typeof verdict.claims.email === "string" ? verdict.claims.email : null; // a person
const service = typeof verdict.claims.common_name === "string" ? verdict.claims.common_name : null; // a service token
```

- The token is the `Cf-Access-Jwt-Assertion` header, or with `cookie: true` the `CF_Authorization` cookie when there is no
  header (the cookie rides on every path of the host; the header only on paths the application covers).
- RS256 is pinned. The issuer must be `https://<team domain>` exactly, with no trailing slash; the team domain may be kept with
  or without the scheme and a trailing slash. The audience is the application's tag. Expiry and not-before allow 60 seconds
  of skew.
- A refusal names its reason: `not-configured`, `no-token`, `malformed`, `algorithm`, `unknown-key`, `signature`, `issuer`,
  `audience`, `expired`, `not-yet-valid`. A pass returns the token's claims.
- The keys come from `https://<team domain>/cdn-cgi/access/certs`, cached per isolate. A kid not in the cache refetches, at
  most once every 30 seconds, so a forged kid cannot hammer the endpoint. A key set that cannot be fetched **throws**: an
  outage is not a refusal.
- What a refusal shows stays with each site.

`accessAdmin` is the admin check txasm, Foxing, Foxhound and Germomics had each copied:

```js
import { accessAdmin, accessSignInUrl, safeAdminNext } from "@dustinedwards/site-runtime/access";
const admin = await accessAdmin(request, env);                                // ADMIN_EMAILS, else ADMIN_EMAIL
const same = await accessAdmin(request, env, { admins: [session.user.email] }); // Access must name this signed-in user
if (!admin) return redirect(accessSignInUrl(request));                        // /admin/access?next=<this page>
```

- `accessAdmin(request, env, { admins })` is `{ email }` or null and never throws. The token is the header or the
  `CF_Authorization` cookie; its email, trimmed and lower-cased, must be in `admins` (a list or a comma-separated
  string, compared in lower case; default `adminEmails(env)`). An empty list admits nobody. Keys that cannot be fetched
  are null, logged as `access_keys_unreachable`.
- Local development: `ACCESS_DEV_BYPASS="1"` passes the first admin with no token, and only on a `localhost` URL, so a
  stray copy of the setting in production does nothing.
- `adminEmails(env)` reads `ADMIN_EMAILS`, else `ADMIN_EMAIL`, split on commas, trimmed and lower-cased.
- `AccessSecrets` is the type a site's `Env` extends: `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`, `ACCESS_DEV_BYPASS?`.
- For a site whose Access application covers one path (txasm: `/admin/access`, which sets the domain-wide cookie and
  comes back), `accessSignInUrl(request, { path })` is that path with the current page as `next`, and
  `safeAdminNext(next, { prefix, path })` is where to land after it: `next` when it is under `prefix` (`/admin`) and not
  the Access path, else `prefix`.
- Admin idle limit: `adminIdle(request, { idleSeconds })` ends an admin's Access session after `ADMIN_IDLE_SECONDS`
  (an hour) without a request, NIST SP 800-63B-4's inactivity timeout at AAL2; Access itself has session lengths but
  no idle timeout, and its 24 hours stays the overall limit. A site calls it in its Worker's fetch for admin paths,
  before the app: `{ idle: true, response }` is a redirect to Access's logout (`ACCESS_LOGOUT_PATH`, which revokes the
  session everywhere), to return as is; `{ idle: false, cookie }` is the Set-Cookie (`__Host-admin-seen`) recording
  this request, to append to the app's response. The last request is that cookie's time when its HMAC, keyed by the
  Access session (the token's `sub` and `iat`), matches; otherwise the token's `iat`. A request with no Access token is `{ idle: false }`.

  A host whose own sign-in is not an Access token on each request (the Capsid Portal, on Access for SaaS with its own
  signed cookie) passes `session: { id, signedInAt }` in its place: `signedInAt` the sign-in time in epoch
  milliseconds, `id` an opaque value only the server can make (an HMAC of the session under a server secret), since the
  seen cookie is keyed by it. A cookie recorded for another session is ignored.

  Background requests do not keep an admin awake. A request with `X-Background: 1` (`BACKGROUND_HEADER`), which the page
  sets on its polling and refresh fetches, or with `Sec-Purpose: prefetch` (a speculative load the browser made, as from
  `./prefetch`'s rules) is checked like any other, so an idle session still ends on it, but it records nothing: an
  hour of a page polling with nobody at it is an idle hour. Only the fetches the page makes on its own carry the
  header; one a person's click starts does not. `Sec-Fetch-Mode` is no help here, since a poll and a click's fetch
  both send `cors`.

  `withAdminIdle(request, handle, { prefixes })` does both around the site's handler for paths under `prefixes`
  (default `/admin`; `["/"]` for a site that is all admin, as Carrel's Desk):

```js
return withAdminIdle(request, () => app.fetch(request, env, ctx), { prefixes: ["/admin"] });
```

A site with two Access apps (two tokens, as dustinedwards.info's `/admin` and `/lab`) runs one check per app, each
with its own `cookieName`, so moving between them never reads the other app's cookie as the last request. The default
stays `__Host-admin-seen`:

```js
const site = () => app.fetch(request, env, ctx);
const lab = () => withAdminIdle(request, site, { prefixes: ["/lab"], cookieName: "__Host-lab-seen" });
return withAdminIdle(request, lab, { prefixes: ["/admin"] });
```

**Tests.** `test/html.test.mjs`, `test/compare.test.mjs` (both the XOR path and a stubbed `crypto.subtle.timingSafeEqual`)
and `test/access.test.mjs` (a key pair made in the test and a fake certs endpoint; `accessAdmin`'s case folding, its
localhost-only bypass, its refusal when the keys cannot be fetched, and `adminIdle`'s timing). Each PLANT test fails when the guard it
names is removed.

## Access drift

`site-runtime-access-drift` (`bin/access-drift.mjs`, logic in `./access-drift`) is the check for I2: it reads a
Cloudflare Access application's policies through the Cloudflare API and compares who they let in with the site's own
admin list, so a person removed from one and not the other is found.

```sh
CLOUDFLARE_API_TOKEN=... ACCESS_CLIENT_ID=... ACCESS_CLIENT_SECRET=... \
  npx site-runtime-access-drift --account <account id> --app "<application name>" --admins-url https://example.com/admin/access-drift
```

- The token needs Access: Apps and Policies Read on the account (and Zero Trust Read when a policy uses an email
  list). It goes to api.cloudflare.com in the Authorization header only and is never printed. `--account` may be left
  to `CLOUDFLARE_ACCOUNT_ID`. The application is found by its exact name.
- Who an Allow policy lets in: its include rules less its exclude rules. An `email` rule is one address, an
  `email_list` rule the addresses on that Zero Trust list, a `group` rule that Access group's include less its
  exclude, read the same way. A reusable policy listed without its rules is read on its own. Any other include rule
  (an email domain, everyone, an identity provider's group) and any Bypass policy lets in people no list can name, so
  it is reported and counts as drift. Require rules only narrow and are not read; Service Auth policies are not people.
- The site's list comes from the site, so no copy of it is kept in GitHub. The site serves it at a path its Access
  application covers (`ADMIN_LIST_PATH`, `/admin/access-drift`, or its own) with `adminListResponse(request, env, {
  admins: adminEmails(env) })`: a GET that Access let through with a service token (a verified Access token for the
  application, `ACCESS_TEAM_DOMAIN` and `ACCESS_AUD`, naming a `common_name` and no person; with `clientId`, that token
  alone) gets `{ salt, hashes }`, a fresh random salt and the SHA-256 of `salt:address` for each admin (`adminHash`).
  Anything else is 404. The job reads it with `--admins-url` and the service token's `ACCESS_CLIENT_ID` and
  `ACCESS_CLIENT_SECRET` (sent as `CF-Access-Client-Id` and `-Secret`; a redirect means Access refused it), hashes each
  address Access lets in with the same salt and compares (`fetchAdminList`, `accessDriftHashed`). The service token is
  let in by a Service Auth policy on the application, which the check does not read as people. On your own machine,
  `ADMIN_EMAILS` or `--admins-file` (one address per line or comma-separated, `#` comments) stand in for the site.
  Addresses compare in lower case.
- Each difference prints as `::error title=I2 access drift::<address or rule> ...`, the address masked
  (`d***@example.com`) because a public repo's Actions logs are public; `--show-addresses` prints it whole on your own
  machine. The difference is one of: let in by Access but not an admin, an admin Access does not let in (from the
  site's hashes only a count: "1 of the app's 3 admins is not let in by Access"), or an open rule. Exit 0 when they
  match, 1 on drift, 2 when it cannot run (no token, no service token, no such application, an API refusal, an empty
  list).

A site runs it daily through devkit's reusable `access-drift.yml`, which fails while a secret or input is missing (no
skip-and-pass), with a caller of a few lines (devkit `examples/access-drift-caller.yml`):

```yaml
name: access-drift
on: { schedule: [{ cron: "17 6 * * *" }], workflow_dispatch: {} }
jobs:
  drift:
    uses: DrDustinEdwards/devkit/.github/workflows/access-drift.yml@<full sha> # vX.Y.Z
    with: { app: example-login, admins-url: "https://example.com/admin/access-drift", account: "${{ vars.CLOUDFLARE_ACCOUNT_ID }}", site-runtime-ref: v0.59.0 }
    secrets: { ACCESS_READ_TOKEN: "${{ secrets.ACCESS_READ_TOKEN }}", ACCESS_CLIENT_ID: "${{ secrets.ACCESS_CLIENT_ID }}", ACCESS_CLIENT_SECRET: "${{ secrets.ACCESS_CLIENT_SECRET }}" }
```

A failed run is the alert. `test/access-drift.test.mjs` runs it against a fake API: direct addresses, a group with its
own exclude, an email list, a reusable policy, a domain rule and a Bypass policy; and the site's hashed list, served to
a service token only and compared by hash.

## What the check requires

`checkSecurityHeaders(headers, { site })` grades a real response against the site's registry entry: the set
`buildSecurityHeaders({ site: entry })` builds, and the opt-ins it declares. Without `site`, `standard` is the floor (default
`STANDARD_SECURITY_HEADERS`) and each opt-in may be passed by name. Each result names the checklist item it proves (`id`:
T2, H1, C4 ...); a `warn` result fails nothing, and `failures` leaves it out.

- Every header in the set, at least as strict: HSTS at least the set's age (and `includeSubDomains` when the set has it),
  framing refused, every feature the set denies denied, and every other header, Referrer-Policy included, exactly the
  set's value. COOP and COEP only on HTML, the kinds they govern; CORP may be `cross-origin` on the kinds `corpFor` names.
- A charset on a text or XML Content-Type; no header from OSHP's remove list (`Server: cloudflare` aside, which
  Cloudflare adds); no deprecated header (`X-XSS-Protection`, `Expect-CT`, `Feature-Policy`).
- Every Set-Cookie `Secure` and with `SameSite` (Strict or Lax, or None with Secure); `HttpOnly` on one whose name says
  session, auth, token, sid, login, csrf or state; a `__Host-` or `__Secure-` prefix unless the entry declines it by
  name; and a response that sets one is `no-store` or `private`. With `upload: true`, the file is `nosniff` and inert (A3).
- An **enforced** Content-Security-Policy, sent once (two headers arrive joined by a comma) with no directive written
  twice. A Report-Only policy alone fails: it blocks nothing.
- A script source list with no `'unsafe-inline'` (unless the site declares `inlineScripts`) or `'unsafe-eval'` in any
  case and no known allowlist-bypass host; `script-src-elem`, `script-src-attr` and `worker-src`, when present, too.
- No `broadSource` in any fetch directive (C5), and no effective `'unsafe-inline'` on style-src unless the site declares
  `inlineStyles` (C11).
- On a registry site, S2 (Integrity-Policy or its Report-Only form, blocking scripts), C3 (`'strict-dynamic'` beside a
  nonce or hash, or `script-src 'none'`), C7 (`require-trusted-types-for 'script'`), C9 (`default-src 'none'`) and I3
  (COEP or its Report-Only form): an error unless met or declined in `deviations` (a warning). A declared opt-in is held
  to its form (a `"report-only"` one read from the Report-Only policy or header) and no deviation excuses it.
- `object-src 'none'`; `base-uri` and `frame-ancestors` `'none'`, or also `'self'` when the site declares `baseUriSelf` or
  `framedBySameOrigin` (with no `site`, either); `form-action` `'self'` or `'none'` when set (an OAuth consent page leaves
  it out on purpose; `'self'` may be followed by the declared `formTargets`); both report sinks, on a registry site
  `/csp-report` and the group `csp-endpoint` (C14); and a `Reporting-Endpoints` that names, with an https URL, every
  group a header reports to: the policy's `report-to`, COEP's `report-to` and Integrity-Policy's `endpoints` (M1).

`checkSecurityTxt({ url, origin, status, headers, body })` grades `/.well-known/security.txt` the same way (D1-D4).

`style-src-attr 'unsafe-inline'` is allowed: several sites emit inline style attributes, and styles cannot run code.

## The live check

`site-runtime-security --origin <origin> [--from <origin>]` (the package's bin) checks one deployed site against its
registry entry, the contract devkit-live runs: `--origin` is the site's address and `--from` where it is served now
(a site before its domain cutover: `--origin https://example.com --from https://example.workers.dev`). Each finding is a line
`::error title=<item>::<proof URL> <detail>` (or `::warning`), the item a checklist id; exit 0 means no errors, 1 errors,
anything else that it could not run.

It makes about 25 requests, one at a time, never following a redirect: `/` (graded with its policy, and fetched twice when
it carries a nonce, which must differ and be on every nonced element; an off-site script or stylesheet without
`integrity` is a warning), a page from `/sitemap.xml` and its trailing-slash twin (the redirect hop must carry HSTS), the
`www.` host for a bare domain, a hashed asset and one other static file the home page names, the asset's `.map` (404), a
missing path, a file under the entry's `uploads` prefix (A3), a cacheable-looking path under `/account/` (X3: not a
cached 200), `http://` (a same-host 301 or 308 to https, workers.dev included),
`/.well-known/security.txt` (`checkSecurityTxt`), HEAD and OPTIONS on `/`, TRACE (405 or 501), an unknown method (400,
405 or 501), GET and OPTIONS with a foreign Origin (R5: no echoed or `null` Allow-Origin, no `*` with credentials), and
`/.git/HEAD` (404), `/.env`, `/.dev.vars` and `/wrangler.jsonc` (never 200). A `::notice` line is a family deviation and
counts as nothing. A redirect to Cloudflare Access is a warning that the page is behind Access, and on that host
Access's own 4xx answers (its no-cache pair, none of the site's set) and its sign-in redirect's echoed Origin are not
graded as the site's; security.txt behind it is an error. A workers.dev host follows one rule (A6): it is noindexed
while, and only while, the entry's `oldSite` still serves the live old site (bsw: biosciencewriters.com), and a
workers.dev copy of a site whose origin is elsewhere is always noindexed. An origin not in the registry is graded
against the bare standard, with a warning.

## Static assets: the `_headers` file

Cloudflare's asset server answers a static file without running the Worker, so the Worker's header set never reaches
it. `headersFile(set, { paths, comment })` (`./headers`) writes the `_headers` file that carries the same set to those
files: `set` on `/*` minus any Content-Security-Policy (a page's policy names what that page loads and may carry a
nonce), then each entry of `paths`, a path pattern and the headers it adds or changes. Cloudflare joins a header that
two matching rules set, so a path that changes a header of the set first detaches the `/*` value with `! Name`.
`comment` lines lead the file as `# ...`. `charset: true` adds a `/*.css`-style rule per static extension giving its
Content-Type `charset=utf-8`, which the asset server leaves out, and `Cross-Origin-Resource-Policy: cross-origin` on
stylesheets, scripts, SVG and fonts (`corpFor`), so another origin or a sandboxed frame may load them; a `paths` entry with
the same pattern is merged into that rule.

```js
import { headersFile } from "@dustinedwards/site-runtime/headers";
writeFileSync("public/_headers", headersFile(SECURITY_HEADERS, {
  comment: "GENERATED by scripts/gen-headers.mjs. Do not edit.",
  paths: {
    "/assets/*": { "Cache-Control": "public, max-age=31536000, immutable" },
  },
  charset: true,
}));
```

Every site writes it with the one bin, from its registry entry:

```sh
site-runtime-headers --site prelum --out specimen/dist/_headers --header "tdm-reservation: 1"
```

The file is `staticHeaders(entry, { headers }).file` (`./static-site`): `buildSecurityHeaders({ site })`, each `--header`
the site adds on top (Prelum's TDMRep header), `charset: true`, and the entry's `assets`: `paths`, the headers a pattern
adds (the build's content-hashed `/assets/*` immutable, CORP on shared images), and for a static site `policy`, its one
page policy built with its policy opt-ins, which goes on a `/*` rule of its own with its Reporting-Endpoints (to
`reportOrigin` when it reports elsewhere) and, beside it, the Report-Only policy carrying what the entry stages. A path
rule that sets its own policy (Prelum's diagrams) detaches the page's. `assets.skipWorker` records the patterns
`run_worker_first` leaves to the asset server, which get the set from this file alone: Capsomer `/assets/*`, Prelum
`/fonts/* /katex/* /images/* /diagrams/*`, Enarratio and Carrel's public page `/fonts/*`, and every file of the Capsid
explorer.

## The Worker in front of a static site

`staticSite(options)` (`./static-site`) is the whole Worker for a site served from Workers static assets (Capsomer,
Prelum's specimen, Carrel's public page, Enarratio's gallery, the Capsid explorer), so each gets what the rendered sites
get. In order: one hop to the canonical address (`canonicalRedirect`, with `canonical` as its options, or `false` for a
site whose pages end in a slash); Content-Security-Policy reports at `reportPath` (default `/csp-report`, limited by a
`CSP_REPORT_RATE_LIMIT` binding when there is one); `/health` (`health`, or `false` for none), `healthResponse` with
`sha` from the `DEPLOY_SHA` var that devkit's shared deploy sets (`sha-var: DEPLOY_SHA`), so its live gate sees the new
deploy serving before it checks the site; the prefetch rules at `/speculation-rules.json` (`prefetch` is
`speculationRules`' options, or `false`). Then the asset. A page gets the `Speculation-Rules` header, so Cloudflare's
generic rules are not the ones used; `Server-Timing` for the asset read; charset=utf-8 and any header of `headers` its
own `_headers` rules left out; and, on a 200, the `preload` Link header, which Early Hints answers with a 103. A path
with no file gets the 404 page (`notFound`, default `/404`) with status 404 and `private, no-store`, so no browser or
proxy keeps a "not found" after the page exists; a page answered to a request with a cookie is `private, no-store` too.
Every other file passes through untouched.

```js
// worker.mjs: the set its _headers file was written from (staticHeaders), with what the site adds on top
import { staticSite } from "@dustinedwards/site-runtime/static-site";
import { prelum } from "@dustinedwards/site-runtime/sites";
import { TDM_RESERVATION_HEADERS } from "@drdustinedwards/site-helpers/robots";
import { PAGE_PRELOADS } from "./headers.mjs";
export default staticSite({ site: prelum, headers: TDM_RESERVATION_HEADERS, preload: PAGE_PRELOADS.header });
```

In wrangler, `run_worker_first` sends the Worker every page and leaves the hashed files to the asset server (for
example `["/*", "!/assets/*"]`); `not_found_handling` may be `"none"` or `"404-page"`.

## Adopting it

1. Add the site's entry to `sites.mjs`, build the set with `buildSecurityHeaders({ site: entry })` and apply it with
   `applyHeaderSet` on every response, redirects included (`applyHeaderSet(response, set)` rebuilds one whose headers are
   immutable and passes a WebSocket upgrade through), and write `_headers` for static assets with `site-runtime-headers`.
2. Build the policy with `buildContentSecurityPolicy` from the site's own list.
3. In CI, run `checkSecurityHeaders(headers, { site })` on rendered responses (see `test/worker/public-csp.test.ts` in
   dustinedwards-info).

## Rate limiter

One exact rate limiter for the sites. A SQLite-backed Durable Object counts fixed windows in synchronous
SQL, so the count cannot race. Each call site says what a failing counter means; the module has no default for it.

Not the Workers Rate Limiting binding (Cloudflare documents it as "permissive, eventually consistent, and intentionally designed to
not be used as an accurate accounting system") and not KV (read-modify-write races).

```js
import { limit, limitedResponse, mustStop, ipKey } from "@dustinedwards/site-runtime/rate-limit";
import { RateLimiter } from "@dustinedwards/site-runtime/rate-limit/durable-object";

export { RateLimiter }; // the Worker exports the class and binds it in wrangler.jsonc

const { key } = ipKey("ask", request);
const verdict = await limit(env.RATE_LIMITER, key, [{ limit: 300, windowSeconds: 3600 }, { limit: 1000, windowSeconds: 86400 }], {
  onUnavailable: "refuse", // or "allow": required
});
if (mustStop(verdict, "refuse")) return limitedResponse(verdict);
```

- `verdict.status` is `"ok"`, `"limited"` or `"unavailable"`.
- `limitedResponse` is a 429 with `Retry-After` set to the seconds left in the window, or a 503 with `Retry-After: 60` when the
  counter is unavailable and the site refuses. Never a success code.
- `"allow"` still returns `status: "unavailable"` and logs one structured line (the key's bucket, never the address or account).
- All rules for a key are checked first; if one is spent none is counted, and a refused request writes nothing.
- `limit(..., { onUnavailable, peek: true })` counts nothing and only says whether the rules are spent (the Durable
  Object's `peek`), for a limit on failures: peek before the attempt, `limit` after a failed one.
- An alarm clears an idle instance's rows after its longest window.
- `emailKey(prefix, email)` is `prefix:` and the SHA-256 of the address trimmed and lower-cased (null for an empty one),
  for a limit per address that never names it; `./sign-in`'s per-address limits use it.
- `matchRule(request, rules)` matches `{ path, prefix?, methods? }` after percent-decoding, collapsing slashes, dropping a trailing
  slash and lower-casing, so `/LOGIN`, `/login///` and `/%4cogin` all match `/login`.

A Worker that already has a Durable Object class it cannot rename (a rename needs a migration) can `extend RateLimiter`; the
counting is in its own `rate_window` table, so the class's other storage is untouched.

**Cost.** Per million allowed requests, one window costs about $1.15 on a Durable Object (one request, one row read, one
row written) against $5.50 on KV; a refused request costs a request and a row read, no write.

**Tests.** `npm test` runs `test/rate-limit.test.mjs`: window edges, a spent rule counting nothing, Retry-After, the fail-closed
and fail-open paths, and the path matcher on an in-memory SQLite (`node:sqlite`).

## Members

The rules every app with staff shares (capsid docs/design/design-identity-roles.md). Each app keeps its own `members` and `member_audit` tables and its own titles; this module
holds the rules, with no I/O and no dependencies, so they are tested once.

Code checks permissions, never titles. A title is a named bundle of permissions on a layer:

| Layer | Title | Set by |
| --- | --- | --- |
| 0 | `primary_owner`, Dustin only | `PRIMARY_OWNER_EMAIL`, deployment configuration; never a row |
| 1 | `owner` | the Primary Owner, on the members page |
| 2 | the app's leads | layers 0 and 1 |
| 3 | the app's members | layers 0 to 2 |

```js
import { defineTitles, resolveActor, can, checkChange, defaultEndDate, auditRow, allowList } from "@dustinedwards/site-runtime/members";

const catalog = defineTitles({
  permissions: ["read", "use_lot", "record_run", "read_all_runs", "edit_inventory", "draft_procedure"],
  titles: [
    { id: "lab_manager", label: "Lab manager", layer: 2, expires: true, permissions: ["read", "use_lot", "record_run", "read_all_runs", "edit_inventory", "draft_procedure", "manage_members"] },
    { id: "lab_worker", label: "Lab worker", layer: 3, expires: true, permissions: ["read", "use_lot", "record_run"] },
  ],
});
const actor = resolveActor(accessEmail, rowFromD1, { catalog, primaryOwnerEmail: env.PRIMARY_OWNER_EMAIL, nowMs: Date.now() });
if (!can(actor, "edit_inventory")) return notFound();
```

- `resolveActor` reads the person's row, which the app loads uncached on every request, so a removal or an expiry takes effect
  on the next click. No row, a removed or expired row, or an unknown title returns null. The Primary Owner needs no row, and a
  row cannot lower them.
- `checkChange(actor, change, context)` is the one place the two rules live: **you manage only people below your own layer**,
  and **you grant nothing you do not hold**. It also refuses any change aimed at the Primary Owner's email, a title change
  without a one-line reason, and an end date past the title's default (shortening is allowed). Owners and the Primary Owner
  hold every permission the app defines and never expire.
- `defaultEndDate` is the first of the app's term end dates after today (after the current end date, to renew). It refuses when
  the Owner has not entered a future date yet, rather than inventing one. A row is valid through the whole of its end date in
  UTC; `reviewOpen` is true from three weeks before it.
- `auditRow` is the `member_audit` row, written in the same batch as the change, with `cloudflare: "pending"` until the sync
  answers. `allowList(rows, nowMs, catalog)` is the email list the app's Access group should hold; the sync itself is Capsid's (ruling 1:
  Capsid is the only holder of the Cloudflare token).

**Tests.** `test/members.test.mjs`. Each rule was planted broken once and seen to fail a test: a lead granting their own layer,
a bundle wider than the granter's, an Owner removing or demoting the Primary Owner (by an `owner` row and by a stray row under
his email), a peer managed, a removed or expired row admitted, the expiry boundary moved a day, an end date lengthened, a
two-line reason.

## The Access sign-in

Every MCP server in the family signs a person in through Cloudflare Access for SaaS (OIDC), one login for all of them, with
`./access-login`:

```js
import { accessSaas, newSignIn, authorizationUrl, finishSignIn } from "@dustinedwards/site-runtime/access-login";

// After consent: the verifier and nonce go in the provider's upstream state, server-side.
const signIn = newSignIn();
const { state, headers } = await env.OAUTH_PROVIDER.beginUpstream(approved.request, { data: signIn, headers: approved.headers });
return redirect(await authorizationUrl(saas, { redirectUri: `${origin}/callback`, state, ...signIn }), headers);
// On /callback:
const { request: original, data } = await env.OAUTH_PROVIDER.finishUpstream(request);
const signedIn = await finishSignIn(saas, { code, redirectUri: `${origin}/callback`, verifier: data.verifier, nonce: data.nonce });
if (!signedIn.ok || !isAdministrator(signedIn.email)) return refuse(original);
```

- The state of a sign-in in flight is not kept here: `@cloudflare/workers-oauth-provider`'s `beginUpstream` and
  `finishUpstream` hold it server-side, bind it to the browser and spend it once. Never put the verifier or the nonce
  in a cookie.
- Every endpoint derives from `ACCESS_TEAM_DOMAIN` (`https://<team>.cloudflareaccess.com`) and the SaaS app's client id.
  A missing setting makes `accessSaas` null, and the door stays shut.
- PKCE (S256) and an OIDC nonce on every sign-in. The code exchange gives up after 15 seconds
  (`token-exchange-unanswered`), so a hung Access does not hold the sign-in.
- The ID token is checked with WebCrypto against the SaaS app's keys, with no JWT library. It must be RS256, from the
  right issuer, for this audience, and within expiry and not-before (60 seconds of skew allowed). The nonce must match,
  `email_verified` must not be false, and an email must be present. An unknown kid refetches once, so a key rotation
  does not lock the door.
- Who may sign in is the caller's to decide; the module admits nobody by itself.

**Tests.** `test/access-login.test.mjs` runs against a key pair made in the test and a fake token endpoint. Each of these
checks was removed once and seen to fail a test: the signature, issuer, expiry, algorithm, nonce and `email_verified`
checks.

## The MCP login and the tool-call log

The MCP servers (Dustin Edwards Admin, Foxing Admin, Foxhound Admin, and Carrel with several people) sit behind `@cloudflare/workers-oauth-provider`
and share everything else in front of it: the consent page, the Access round trip, the administrator check, the
registration allowlist and the tool-call log. Each server passes what is its own:

```js
import { isAdminUser, loginHandler, registrationRefusal } from "@dustinedwards/site-runtime/mcp-login";

export const defaultHandler = loginHandler({
  name: "Sample Admin",
  scopes: { read: "sample.read", write: "sample.write" },
  about: "<p>Sample Admin runs sample.example.com. It will always be able to read. Changes need the box below.</p>",
  admit: isAdminUser,
});
// In the provider's options:
clientRegistrationCallback: ({ clientMetadata }) => {
  const why = registrationRefusal(env.DCR_REDIRECT_URIS, clientMetadata);
  return why ? { code: "invalid_redirect_uri", description: why } : undefined;
},
```

- `loginHandler` is the provider's `defaultHandler`: `/health`, the consent page and its form on `/authorize`, and
  `/callback`. The callback address is `PUBLIC_ORIGIN` (or the request's origin) plus `/callback`. A missing Access setting
  answers 503: not configured means not open.
- Least scope first: every grant holds the read scope, and the write scope only when the administrator ticks the box
  (it starts ticked only when the client asked for it). The grant's props are `{ email, scopes, client, clientId }`,
  `client` being the name the consent page showed, for the server's own log. The page says who publishes a CIMD client
  (its metadata URL's host) and that a registered client's name is its own claim.
- `admit` decides who is let in; `isAdminUser` is `ADMIN_EMAIL`, compared without case, and an unset value admits nobody.
  A server with several people returns an object instead of `true` (Carrel's `{ personId }`): it admits, and its fields
  join the grant's props for the server to check again on every request. `admits: { consent, refusal }` then says who
  is let in, on the consent page and in the refusal (default: the configured administrator). `wantsWrite(requested)`
  decides whether the write box starts ticked (default: the client asked for the write scope), and `health(env)` answers
  `/health` (default: `healthResponse({ sha: env.DEPLOY_SHA })` from `./health`, so an MCP Worker's /health is
  `application/health+json`, no-store and noindex, with the deployed commit when `DEPLOY_SHA` is set). `revokeExistingGrants: false` keeps the user's earlier grants for the same client (the
  provider's default revokes them), for a server whose two connectors share one client id.
- The consent POST must be `application/x-www-form-urlencoded` (else 415) and at most 64 KiB (else 413), read to the
  ceiling before it is parsed.
- The page's one inline style is `CONSENT_STYLE`, rendered exactly, so the server's Content-Security-Policy trusts it by
  `scriptHash(CONSENT_STYLE)`. Give the page no `form-action`: the approve POST redirects through Access to whatever
  redirect URI the client named. A loopback callback or an app's own scheme (an app on the person's computer) gets a
  line saying so. `describeRedirect(uri)` is that check for a server with its own consent page: `{ host, local,
  warning }`, `host` the redirect's host (the scheme, as `cursor://`, for an app's scheme) and `warning` the line to
  show when `local`, else null.
- `registrationRefusal` allows a dynamic client registration only when it names one to five redirect URIs, each in the
  list exactly; the list is separated by commas or spaces and keeps only https callbacks, and an empty one refuses all. `DCR_CALLBACKS` holds the callbacks that are the same for every user (Grok,
  ChatGPT's fixed one, Gemini Enterprise), for a server that registers them: pass
  `[...DCR_CALLBACKS, env.DCR_REDIRECT_URIS].join(",")`. `registrationLimited(request, env.OAUTH_KV)` counts each
  `/register` in KV (five an hour per address, thirty a day in all) and answers the 429; call it before the provider.
- `./audit-log` is the append-only tool-call log: export `ToolCallLog` as the Durable Object bound to `TOOL_CALL_LOG`,
  then `appendAudit(env, row)` before (`started`) and after (`finished`) each call, or once for a `refused` one, with
  `loggedArgs` and `loggedResult`. A string argument over 200 characters is stored as its length and a SHA-256 prefix.
  A row also carries the server's name and version, the OAuth client id and a correlation id (`correlationId(meta)`, the
  trace id of a `_meta.traceparent` when the client sent one), and a hash chain over the rows: `verifyAuditChain(rows, key)`
  names the first row that was changed or removed. Bind the Worker secret `AUDIT_CHAIN_KEY` before the first row and the
  chain is HMAC-SHA-256 under it, which an editor of the table without the secret cannot recompute; without it the chain
  is plain SHA-256 and only catches an edit nobody recomputed. Neither catches rows cut off the end. Besides the call phases, `recordAudit` writes `sign-in`,
  `scope-challenge` and `rate-limited` rows; `loginHandler({ audit: { name, version } })` writes one per sign-in.

**Tests.** `test/mcp-login.test.mjs` runs the handler against a fake provider and a fake Access. The scope from the box,
the administrator check, the exact registration match and the registration limit were each removed once and seen to fail a
test.

## The AI and MCP live check

`site-runtime-ai-audit --origin <origin> [--from <host>] [--kind worker|site|static]` is area 11's check in devkit's daily
run (one areas.json entry per kind, with `--kind` in its `args`). An origin that publishes OAuth protected-resource metadata
is probed as an MCP server, without a token: its resource and authorization-server metadata (A1, A4), the 401 challenge
(A2), `no-store` on `/authorize` (A8), a foreign `Origin` (P10), GET on the endpoint (P5) and `/health` (S8). A `worker`
that publishes none is an A1 error. With no `--kind`, a metadata path that answers anything but 404 or a JSON object is
an A1 error, so a server whose metadata broke never passes as a site. A site has nothing more for this check.
Findings print as `::error title=<item>::<url> <detail>`, with `%`, CR and LF escaped as GitHub requires; it exits 0
clean, 1 on an error, 2 when the origin does not answer.

## The MCP server scaffold

`./mcp-server` is the rest of what the admin MCP servers (and Carrel's AI door, for the era router) had each copied. No
dependency: the caller hands in the SDK's two functions.

```js
import { authorizeCall, callApi, checkRateLimit, mcpScopes, refuse, routeMcpEra } from "@dustinedwards/site-runtime/mcp-server";
import { isLegacyRequest } from "@modelcontextprotocol/server";
import { createMcpHandler } from "agents/mcp/server";

export const SCOPES = mcpScopes("sample"); // { read: "sample.read", write: "sample.write", all }
return routeMcpEra(request, env, ctx, { factory, options: { route: "/mcp" }, createMcpHandler, isLegacyRequest });
const limit = await checkRateLimit(env.MCP_RATE_LIMIT, `admin:${email}`); // { allowed, retryAfter }
const answer = await callApi(env, { binding: "SITE", token: "OPERATOR_TOKEN", api: "The operator API", userAgent }, "/api/operator", { json: { tool, args } });
const refusal = authorizeCall(env, caller, SCOPES.write, { site: "sample.example.com", scopes: SCOPES });
```

- `routeMcpEra` sends a request the SDK's `isLegacyRequest` calls legacy (2025-11-25, `initialize`) to a
  `legacy: "stateless"` handler and everything else to `legacy: "reject"`, the stateless 2026-07-28 server. Its removal
  condition is in its header: stop passing `isLegacyRequest` when the probe shows the target clients opening with
  `server/discover`; the router is then modern-only.
- `callApi` is the API leg's transport over a service binding to `SITE_ORIGIN + path`. It throws `ApiLegError` (`kind`
  `unconfigured`, `unreachable` or `malformed`) for a missing binding, origin, token under 32 characters or `require`d
  var, a failed fetch or a body that is not JSON (its `status` then the HTTP status), and returns `{ status, ok, body }` otherwise, so a refusal by the API is
  an answer the server relays verbatim. `anonymous: true` sends no bearer (a public health read).
- `checkRateLimit` is 30 requests a minute per identity on the family's limiter. A lower `perMinute` (registration's 5)
  is honored and a higher one is not; a missing or failing binding refuses, with `retryAfter` 60. `refuse` is the
  plain-text, `no-store`, `noindex` answer to go with it.
- `authorizeCall` is the per-call check (rule 12.1): a caller, the administrator (`isAdminUser`) or a well-formed agent
  principal, and the scope the tool needs. A server with several people, whose door already verified the person, passes
  `{ kind: "person", email, clientId, scopes }`, and only the grant's scopes decide. `callerName` is its audit name
  (`access:<email>` for an admin or a person, `agent:<name>`).
- Each tool declares `scope: "read" | "write"` (or a function of its arguments); `toolScope` reads it and never the
  `readOnlyHint` annotation, and a tool with none is refused. `toolsForGrant` drops what a grant cannot call.
  `toolScopeChallenge(env, server, tool)`, passed as `registerTool`'s `scopeChallenge`, makes the SDK answer a write call
  on a read grant with 403 `insufficient_scope` naming every scope it needs, so the client re-authorizes.
- `invokeTool(env, server, { caller, tool, args, meta, run })` is the whole call: the scope check, a `refused` row, or a
  `started` row (the call is refused if it cannot be written), the run, and a `finished` row, written as an error before a
  throwing handler's exception goes on.
- `audienceRefusal(auth, resource, scope)` answers 401 `invalid_token` to a token minted for another server (the
  provider checks this too), `unauthorized` builds a 401 with `resource_metadata` and `scope` for a door the provider
  does not guard, `mcpOriginRefusal(request, allowed)` answers 403 to a foreign `Origin` (a missing one passes), and
  `mcpCacheHints({ ttlMs, shared })` is the `ttlMs` and `cacheScope` for list results, `private` unless listed.

- `withMcpHeaders(handler, { site, securityTxt, reportPath, allowReport })` wraps the door's whole fetch handler: every
  response, a 404 or a library's redirect included, carries the entry's full set, `noindex`, `no-store`, the consent page's
  hashed-style policy (no `form-action`, since approving posts into a redirect chain) or `default-src 'none'` for the rest,
  both report sinks and `Reporting-Endpoints`. It also answers `/.well-known/security.txt` and the report path, so a door
  needs no copy of its own. A 101 upgrade passes as it is.

**Tests.** `test/mcp-server.test.mjs`, once; the servers' own copies of these tests go when they adopt it.
